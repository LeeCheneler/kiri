# Kiri — Design Notes

> *Kiri* (キリト) — Short for Kirito, the protagonist of *Sword Art Online*. Always wanted to call my dog Kiri.

## Concept

A local-first, git-based tool for personal automation. Scripts, AI workflows, and agentic chat invoked by hand. A feed UI streams activity, and each run can surface recommended follow-up runs as one-click trigger buttons on its detail page. Single user (me), running while the app is active.

Kiri has **two pillars**, both feeding the same activity feed:

- **Workflows** — the original pillar. YAML-defined linear pipelines (`script → ai → script`) invoked by hand. Deterministic, fixed-shape; an `llm:` step is one prompt in, text out. The pillar everything below under *Architecture* and *AI integration* describes.
- **Agentic sessions** — a multi-turn agentic chat against a configured model: system prompt, tools, streaming, images. A conversation, not a pipeline. Described under *Agentic sessions*.

The two are **separate concepts with separate config, storage, execution, and UI** — they share infrastructure (config dir, SQLite, the event bus, the LLM provider registry) and the activity feed, but a workflow is never an agent and an agent is never a workflow. They stay decoupled by design; the only bridge is the first-party *workflow tools* a session's model can call — listing and running workflows, and authoring their YAML files — tool invocations, not a merging of the two models.

What sets kiri apart from Windmill, Kestra, n8n, Inngest et al. is the **feed-first UI** — activity stream as the primary surface, not a node-graph canvas.

## Core principles

- **App-active scope.** Everything runs while the app is open. No daemons, no launchd, no overnight execution. Sleep/wake is not our problem.
- **Single user.** No auth, no multi-tenancy, no scaling.
- **Git as source of truth.** Workflow definitions, prompts, and scripts live in a git repo.
- **Linear pipelines only (workflows).** Workflows have no branches, no conditionals, no fan-out/fan-in. `script → ai → script` covers most real cases. (Agentic sessions are iterative by nature; this constraint is a property of the workflow pillar, not of kiri.)
- **Everything in the workflow pillar is a workflow.** A workflow is N≥1 steps. Single-step workflows wrap "just run a script" cases. Todos invoke workflows. Manual menu items are workflows. One concept, uniform treatment — within the workflow pillar.
- **Two pillars, no crossover.** Workflows and agentic sessions are independent. They share infrastructure and the activity feed, never each other's execution, config, or storage. Don't reach for a workflow primitive to build a session feature, or vice versa.

## Design invariants

Constraints, not work items — they hold across the whole system:

- Standard step envelope (`status`, `output`, `error`, `traces`), never deferred per step.
- Workflow YAML validated against a Zod schema; the top-level shape is fixed (`steps`, `inputs`, `summarize`, `articles`, `description`, `group`) but step `env:` contents are bundle-defined and not validated by kiri.
- No shell interpolation of inputs anywhere — argv arrays and env vars only.
- Kiri is a CLI launched per-workspace; workflow definitions live in `<workspace>/workflows/`. No global cross-repo store.
- Repo-scoped runtime state lives in `<workspace>/.kiri/` (gitignored).
- Workflow definitions load into an in-memory registry; there is no `workflows` table — YAML files are the only source of truth.
- Every run snapshots the resolved workflow definition and the data-repo git ref (HEAD + dirty flag) at start; feed entries reflect the workflow shape that ran, and the sha pins the working tree for reproduction.
- Per-run scratch directory; steps never run with cwd of repo or home.
- Per-step env scope; user `env:` applied first, kiri- and OS-controlled vars overwrite on collision; `KIRI_` prefix reserved.
- Step output renders as plain text in the UI; markdown rendering is reserved for `articles:` articles and `summarize:` summaries, routed through the same sandboxed renderer.
- Session filesystem access is opt-in and sandboxed: the filesystem tools exist only when `filesystem.allowed_directories` is declared in `kiri.yaml`, every model-supplied path — including one that doesn't exist yet, and a relative one, which resolves against the session's working directory — must resolve, through symlinks, to inside a declared directory, and `.git` internals and secret-bearing files (`.env*`, `.kiri/mcp-credentials.json`) are unreachable. Each session carries a working directory inside that sandbox, seeded from `filesystem.default_working_directory` (or the first allowed directory), moved only through the sandbox-validated `set_working_directory` tool, and re-checked against the live sandbox before every turn — a turn whose directory has gone stale refuses to play, announcing and clearing it so the next message self-heals from the configured default, rather than silently working elsewhere. Reads are pre-authorised by the declared sandbox; every mutation (write, edit, create, delete) asks per call by default.
- Session shell access is opt-in and approval-gated: `run_command` rides the same `filesystem.allowed_directories` sandbox as the file tools — one declaration enables the whole surface — and only a command's *working directory* is confined to it (the session's working directory unless the call says otherwise) — what the command touches is not — so every call asks by default, with the core prompt's command-safety rules the first line of defence in front of that approval. The opt-in `auto` permission relaxes only the prompting, never the boundary: a deterministic screen and a fail-closed model judgement decide per command whether to run or fall back to the same approval.
- Delegation never widens what runs unprompted: a delegated child session holds only tools whose standing permission is already `allow` (`ask` and `auto` tools are absent — a worker has no one to ask), never `delegate` itself, and a parent-turn cancel cascades into its children.

## Architecture

### Workflow definition

YAML files validated against a Zod schema. No custom DSL.

```yaml
name: pr-review
description: Review a pull request and summarise findings.  # optional, shown on the workflow page
group: Dev                 # optional, buckets related workflows in the catalog + page eyebrow
inputs:                    # optional — parameters collected via a modal at invocation
  - name: pr_number
    description: The PR to review
    required: true
steps:
  - use: fetch-pr           # script bundle: bundles/fetch-pr/run.sh
    name: Fetch the PR      # optional short label, shown as the step title in the UI
    env:
      PR_NUMBER:
        input: pr_number    # resolved at spawn from the run's inputs snapshot
  - use: claude-code        # script bundle: bundles/claude-code/run.sh (example, see examples/)
    env:
      PROMPT_FILE: prompts/pr-review.tpl
      MAX_TURNS: "50"
  - llm:                    # first-party LLM completion — model from kiri.yaml
      model: anthropic:claude-haiku-4-5
      prompt_file: prompts/pr-summary.tpl
  - sh: |                   # inline shell — sugar for trivial steps
      echo "review complete"
      date
articles:                  # optional: long-form markdown articles
  - slug: digest
    name: "PR Review Digest"
    use: claude-code
    env:
      PROMPT_FILE: prompts/pr-digest.tpl
summarize:                 # optional one or two sentence feed summary
  llm:
    model: anthropic:claude-haiku-4-5
    prompt: "One feed sentence on this digest: {{DIGEST}}"
  env:
    DIGEST:
      article: digest
```

A step is exactly one of three shapes:

- `{ use: <name>, name?, description?, env?: { ... } }` — references a **script bundle** at `bundles/<name>/run.sh`. The bundle is a folder containing at minimum `run.sh` plus any sidecar files it needs (prompt files, generated settings, README documenting the bundle's env-var contract).
- `{ sh: <string>, name?, description?, env?: { ... } }` — inline shell script, run via `sh -c`. Sugar for one-shots that don't deserve their own bundle. Multi-line via YAML's `|` block scalar.
- `{ llm: { model, prompt? | prompt_file? }, name?, description?, env?: { ... } }` — **first-party LLM completion** against a model declared in `kiri.yaml` (see *AI integration → LLM providers*). `model` is a `provider:model` id; the prefix must name a registered provider or the workflow fails to load. The prompt is inline (`prompt`) or a workspace-root-relative file (`prompt_file`) — declaring both is a schema error, and a declared `prompt_file` must exist on disk at load. `steps:` and `articles:` require one of the two; `summarize:` may omit both, falling back to a baked-in summary prompt.

The optional `name` is a short label rendered as the step's title in the Schema tab and the run timeline; it falls back to the bundle reference, the llm model id, or the script's first non-empty line. `description` is longer detail shown when a step's row is expanded. The optional `id` (`^[a-z][a-z0-9_-]*$`, unique within the workflow) names the step so later steps can reference its stdout via `{ step: <id> }` env refs; `summarize:` cannot declare one — nothing runs after it to reference its output.

A main `sh:`/`use:` step may additionally declare **`outputs:`** — a list of named values (same grammar as step ids, unique within the step) it promises to emit via the `kiri-output <name> <value>` helper. The runner writes per-run shims (`.bin/` inside the scratch dir, regenerated every run and torn down with it) and prepends that dir to every step's PATH; the helper execs back into the kiri binary's hidden `__output` command, which appends `{ name, value }` JSON lines to the step-scoped `$KIRI_OUTPUTS_FILE` — set only on declaring steps, so a stray `kiri-output` in an undeclaring step exits non-zero and fails a `set -e` script at the call site. Declaring outputs requires an `id` (they are referenced as `{ step: <id>, output: <name> }`, so an undeclared-id producer is unaddressable — a load error, mirroring the summarize-id rule), and the declaration is a contract: an ok exit missing a declared name flips the step to `failed` before its row settles, blaming the producer rather than a downstream consumer. Undeclared emissions warn and drop; re-emission overwrites (last wins). Ingested maps persist on `run_steps.outputs` and render in the step's expanded run-page row above the raw streams. `llm:` steps have no file channels and cannot declare outputs — a completion's single product is its text.

`env:` is a flat map — each value a literal string or a structured reference (see *Invocation & inputs*) — passed to the bundle (or inline shell) as plain env vars. Each bundle defines its own contract for what keys it expects; kiri doesn't validate config contents. Kiri's own scoped vars (`KIRI_RUN_ID`, `KIRI_STEP_INDEX`, `KIRI_REPO_ROOT`) and OS essentials (`PATH`, `HOME`, `USER`, `LOGNAME`) are applied **after** user env at spawn time, so a workflow can't override them. The `KIRI_` prefix is reserved — workflow `env:` keys starting with `KIRI_` are rejected at load time.

Two workflow-level sibling fields run alongside `steps:`:

- **`summarize:`** — a single `{ use | sh | llm, env? }` entry executed after `steps:` and `articles:` complete, only when the run is still `ok`. Its stdout becomes the run's one-or-two-sentence summary, rendered on the activity feed row and at the top of the run detail page. Like every phase it declares its data through env refs — typically `{ article: <slug> }` for the run's finished document or `{ step: <id>, output: <name> }` for a headline number — so a summary prompt carries exactly what it needs rather than a whole-run digest. Failure is non-fatal: the run's work already completed, the summary just stays empty.
- **`articles:`** — an array of named long-form markdown articles. Each entry has the shape `{ slug, name?, use | sh | llm, env? }`. Each runs in declared order, serially, via the same `runStep` path as a regular step, after `steps:` and before `summarize:` so articles reach the summariser via `{ article: <slug> }` refs. Articles only run when the steps pipeline is `ok` — a failed or cancelled pipeline skips them. The run is fail-fast end to end: a failing article entry flips the run to `failed` and halts the remaining entries and the summariser, the same way a failing step halts the pipeline. Articles are stored as rows in `articles` (linked to their producer via nullable `runId`/`sessionId` columns, XOR-checked — agentic sessions write the same table through their first-party article tools, see *Agentic sessions → Session articles*), surfaced as a stacked list on each activity-feed row, on the run detail page as a stacked list beneath the run's summary and as the "Articles" phase group (an article entry's expanded row links through to its article), and rendered on dedicated `/runs/:id/articles/:slug` pages via a sandboxed markdown parser. The article page lifts the body's first markdown `# heading` out as the page title — dropping any preamble before it — carries an eyebrow naming the kind alone (`Article`) — the breadcrumb above it already names the container, as a link, and the stored article `name` would be a second name for one document — and treats the body's `##` headings as the sections that fill the page's table of contents; a body with no `# heading` falls back to the article name for its page title. Each surface that lists articles shows the article body's first markdown `# heading` as a sub-byline (when present) so identically-titled articles from the same workflow are distinguishable. Article markdown may embed fenced `chart` blocks — Vega-Lite JSON specs rendered inline as SVG charts through that same parser, with the charting library code-split so it loads only for articles that use one — and fenced `mermaid` blocks, rendered as diagrams (with a tab to read the source and an enlarge-to-modal action) through mermaid in its `strict`, DOMPurify-sanitising mode, likewise code-split so the diagram library loads only for articles that use one.

Both fields share the same load-time validation as `steps:` (a step is exactly one of `use:` / `sh:` / `llm:`, `KIRI_` prefix banned on `env:` keys; a missing `use:` bundle, an unknown llm provider prefix, or a missing `prompt_file` is a workflow load failure). A failing summariser is non-fatal — its error stays on the step row but the run terminal status is unaffected. A failing article entry flips `runs.status` to `failed` and halts everything after it.

The script bundle is the primitive for everything kiri reaches by spawning a process; first-party `llm:` steps cover the plain-completion case without forcing a bundle. The repo's `examples/` carries `claude-code` and `lm-studio` starter bundles; forking one for a new runtime is `cp -r` and editing the script. For a **script step** kiri stays runtime-blind: it spawns `run.sh`, captures the envelope, and stays out of the way. An `llm:` step is the deliberate exception — kiri makes the completion call in-process against the configured provider — but its result maps onto the same envelope, so everything downstream (traces, `articles:`, `summarize:`) is identical to a script step's.

Rationale for YAML over TS: workflow files live in arbitrary user repos, but kiri ships as a single Bun-compiled binary. Resolving a TS `import { defineWorkflow } from "kiri"` from those repos would require both a Bun plugin baked into the binary to intercept the import *and* generated `.d.ts` files dropped into each repo for IDE support — both maintenance costs that compound forever. YAML is pure data, validated at load time, and a JSON schema can be published alongside the binary for editor LSP integration with no per-repo footprint.

### Standard step envelope

Every step returns the same shape. Designed in early — painful to retrofit.

```ts
{
  status: "ok" | "failed",
  output: string,          // captured stdout — what { step: <id> } refs resolve to
  error?: { message, stack? },
  traces: { stdout, stderr, durationMs, usage? },
}
```

Full I/O captured at every step. Linked from the corresponding feed entry for debugging and replay. `traces.usage` carries token counts and is present only on `llm:` steps (see *AI integration → LLM step execution*).

### Execution semantics

- **Concurrency:** runs are independent — invoking several workflows (or the same one twice) runs them concurrently. There is no global cap or queue.
- **Errors:** the run is fail-fast — a failed step halts the pipeline, skips `articles:` and `summarize:`, and marks the run failed; a failed article entry does the same for what remains. The feed entry shows the error; re-run manually from the run page.
- **No auto-retry, no DLQ, no fan-out** in v1.

### Invocation & inputs

Runs are invoked manually — from the workflow catalog, by re-running an existing run, by triggering a recommendation, or from an agentic session through the first-party `run_workflow` and `rerun_workflow` tools (see *Agentic sessions → Tools*). There is no time-based or file-based triggering: under the app-active scope a scheduler would only ever fire while the user is already at the keyboard, where clicking Run is the same gesture for no extra capability. Polling shapes (webhooks, inboxes) are served by a workflow whose first step does the poll, invoked when the user wants it.

A workflow optionally declares `inputs:` — named parameters collected at invocation time, so one definition can be aimed at many targets (one `pr-review` workflow with a `pr_number` input reviews any PR, instead of one YAML file per PR).

- `inputs:` is an array of `{ name, description?, required?, default?, options? }`. Values are strings.
- A workflow with no `inputs:` runs immediately on invoke. One with `inputs:` collects values via a form before the run starts — `required` inputs must be filled, `default` pre-fills the field.
- An input can declare a fixed list of allowed strings via `options:`. The invoke modal then renders a picker constrained to those values instead of a text field, the declared `default` (if any) must be one of the entries — enforced at load time — and any value supplied at invoke must also be one of them.
- Step `env:` values are a literal string or a structured reference: `{ input: <name> }` to a declared input, `{ step: <id> }` to an earlier step's stdout (byte-for-byte — never trimmed or truncated), `{ step: <id>, output: <name> }` to one of that step's declared named outputs (see the `outputs:` contract under *Architecture → steps*), or `{ article: <slug> }` to an already-produced article's markdown (articles entries may only reference earlier siblings; summarize may reference any; main steps may not use article refs). The reference graph is validated at load time — unknown ids/slugs, refs to output names the target step doesn't declare, and self/forward references fail the workflow — and the fail-fast lifecycle guarantees every ref target completed `ok` (including having emitted every declared output) before its consumer spawns, so run-time resolution is total. A ref-resolved value that pushes a spawned step's env past the OS exec size limit (~1 MB ARG_MAX) fails the step with an error naming the largest entries instead of an opaque E2BIG; `llm:` steps resolve refs in-process and are exempt. At run-start the runner resolves each declared input to a final value (supplied at invoke, otherwise the input's `default`) and snapshots the resolved `Record<string, string>` onto `runs.inputs`. At spawn the runner walks each step's, article entry's, and summarise's `env:`, replacing every `{ input: <name> }` entry with the snapshotted value; kiri-scoped vars and OS essentials overlay afterwards, so user env never wins on collision.
- Input values are snapshotted onto the `runs` row, so the feed shows what a run was invoked with and a re-run can pre-fill the form.

### State storage

State lives in three tiers, by what kind of state it is:

- **In git** — workflow definitions (`.yaml` files), script bundles (`bundles/<name>/`), prompt files, sandbox profiles. Everything that benefits from review and version history.
- **In SQLite** — runtime state: runs and their steps (metadata + envelopes), articles, recommendations, sessions and their messages. Single file in the data dir, queryable, indexed, transactional. **bun:sqlite** as the driver (synchronous, fast, statically linked into the Bun runtime), **Drizzle** for schema and migrations — plus one surface Drizzle can't model: `search_fts`, a hand-migrated FTS5 virtual table that SQL triggers keep in step with articles, session messages, and run summaries, backing the UI's search (see *UI*). Schema changes to those three tables must keep its triggers in step.
- **On disk (data dir)** — large blob payloads referenced by path from SQLite rows: full CC transcripts, big stdout dumps, anything that'd bloat the DB. Same pattern CI systems use to keep the DB lean.

Pragmatic v1 simplification: skip the disk-blob split initially. Put traces straight into SQLite TEXT columns. Move to disk-backed blobs only when a "last 50 runs" feed query starts dragging on trace payloads — probably won't for months.

### Workflow registry & run snapshots

Workflow definitions are YAML files in `workflows/` — the single source of truth, with no SQL representation. There is **no `workflows` table**. On startup — and on file change, the watcher is always on — the loader scans the directory top-level, parses each file, validates it against the workflow Zod schema, and hydrates an in-memory registry; runs reference workflows by name only.

When a run starts, the executor captures three things to pin the run's context:

- The resolved workflow definition (name, steps, summarize, articles) onto the `runs` row as `definitionSnapshot`. Feed entries always show the workflow shape that ran, even if the YAML file is later edited or deleted (UI shows a "(deleted)" badge when the registry no longer has the name).
- The resolved input values onto `runs.inputs`. Null when the workflow declared no `inputs:` block; otherwise a `Record<string, string>` with one entry per declared input that resolved to a value (supplied at invoke or via the input's `default`). The same snapshot is consulted when resolving `{ input: <name> }` env references at every step's, article entry's, and summarise's spawn.
- The data repo's git ref at run-start: the HEAD commit (`runs.gitSha`) plus a `runs.gitDirty` flag for uncommitted changes. The data dir is already a git repo by convention, so a single SHA pins every file the run could possibly have read — bundle scripts, prompts, anything `run.sh` resolves at runtime. The sha and dirty flag are captured for reproduction (`git checkout <sha>`); they are not surfaced in the run detail UI.

Kiri does not snapshot individual bundle files or prompts into the database. Reproducing what ran means `git checkout <sha>` in the data repo. Both `gitSha` and `gitDirty` are nullable so a non-git data dir is a first-class state, not an error — the run loses the reproducibility affordance but everything else works.

Re-running an old run uses the *current* definition and *current* working tree, not the snapshot. Replay-from-snapshot is out of scope for v1.

## Recommendations

Workflows can surface proposed follow-up workflow invocations alongside the run that produced them. A run that aggregates open PRs, for example, can emit one recommendation per PR pointing at a `pr-review` workflow with `pr_number` pre-filled — turning the aggregator's output into a launch pad for one-click follow-ups.

Recommendations are not a global queue. There is no inbox, no right-rail list, no lifecycle state machine. Each recommendation belongs to its producing run, surfaces on that run's detail page, and is acted on or ignored in place. The shape mirrors `articles:`: emit-time output, persisted as rows linked to the run.

### Emission

A step emits through the `kiri-recommend` shim (per-run PATH, exec into the binary's hidden `__recommend` command), which validates its flags and appends one schema-shaped JSON line per call to the step-scoped channel file in `KIRI_RECOMMENDATIONS_FILE`:

```sh
kiri-recommend --workflow "pr-review" --title "Review PR #123" \
  --description "+500/-200, refactor user auth" --input pr_number=123
```

A malformed call exits non-zero without writing, so emission errors surface at the producing line under `set -e` rather than as silent ingest skips.

Per-line fields: `title` (required), `workflow` (required — name of the workflow to invoke), `description` (optional — displayed under the title), `inputs` (optional `Record<string, string>` pre-filled into the invoke modal). Only the main `steps:` get the env var — `articles:` and `summarize:` do not emit recommendations. A failed step's file is discarded; only `ok` steps contribute rows. Malformed lines are logged and skipped without failing the step retrospectively.

### Storage

Stored in a `recommendations` table linked to the producing run via `runId`, with `index` preserving emission order. Each row carries the emitted payload plus two nullable mutables: `actionedRunId` and `actionedAt`, set when the user triggers the recommendation. No state machine; the only transition is "untriggered → triggered (with a run id pinned)." Indexes on `(runId)` for the detail-page read and `(actionedRunId)` to keep the cascade cheap on run delete.

### Actioning

On the run detail page, recommendations render as a "Recommended" section beneath the run's phases. Each entry shows title + description and a trigger button. Clicking the button opens the standard invoke modal pre-filled with the recommendation's `workflow` + `inputs`; the user can edit before confirming, same gesture as a normal invoke. On confirm, the runner spawns the workflow and the recommendation row's `actionedRunId` + `actionedAt` are written. The trigger button flips into a status-badged link to the spawned run.

If the actioned run is later deleted, `actionedRunId` and `actionedAt` are nulled in the same delete transaction, restoring the recommendation to triggerable. Rerun reuses the run id, so a rerun of an actioned run leaves the recommendation's link intact — same behaviour as everywhere else: the destination mutates but the link still works.

A recommendation whose `workflow` is no longer in the registry renders the trigger button disabled with a "workflow not found" tooltip — same affordance as the "deleted" badge on feed rows for missing workflows.

The feed entry surfaces a small count when a run has recommendations ("3 recommendations" in the row's byline), signalling to click through to the detail page.

## AI integration

### LLM providers (in `kiri.yaml`)

First-party LLM steps reference named endpoints declared under `providers:` in the workspace-root `kiri.yaml` — kiri's structured config file (providers today; tools and settings will join them as siblings). It's a `providers:` map keyed by a name of your choosing:

```yaml
providers:
  anthropic:
    type: anthropic                  # required — anthropic | openai | openai-compatible
  work-openai:
    type: openai
    api_key: { env: WORK_OPENAI_KEY }
  local:
    type: openai-compatible
    base_url: http://localhost:1234/v1
```

- **File name.** The canonical name is `kiri.yaml`; `kiri.yml` is accepted too. If both exist, `kiri.yaml` wins and kiri logs a warning so the duplicate can be removed.
- **Scaffolded on first launch.** Kiri writes a commented `kiri.yaml` (every entry commented out) when a workspace has neither `kiri.yaml` nor `kiri.yml`, so a fresh workspace gets a self-documenting skeleton with no `kiri init` step. It never overwrites an existing file, and an empty or comment-only file loads as "no config".
- **`type` is always required** and selects the API the endpoint speaks; there is no inference from the entry's key. Each entry is a discriminated union on `type`, so the published JSON Schema enforces every rule in-editor — notably that `openai-compatible` requires a `base_url`.
- **`api_key` is an `{ env: <NAME> }` reference only**, never a literal key. This mirrors the `{ input: }` idiom in workflow `env:` and keeps secrets out of the git-tracked YAML. When omitted, `anthropic`/`openai` fall back to the conventional `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`; `openai-compatible` needs no key.
- Kiri reads the config at startup into an in-memory registry. A **missing file is first-class** — an empty registry, not an error. A present file is validated, and a declared `{ env: }` ref must name a variable set in the kiri process or the load fails with the offending key named — the same posture as a workflow referencing a missing bundle. Only *declared* refs are checked at load; conventional fallbacks resolve when a provider is used. Resolved key **values are never persisted, snapshotted, or echoed in errors** — the registry keeps only the env var's name.
- **Env source.** Kiri loads `.env` from the workspace root — the resolved config dir, not the launch cwd — at startup, so a workspace pinned via `KIRI_CONFIG_DIR` gets its own `.env` regardless of where kiri was launched from. The variables your `{ env: }` refs name resolve from there or the ambient environment. Existing variables win: an ambient export of the same name is left untouched, and an absent `.env` is a no-op.
- **Editor support.** Kiri publishes `.kiri/kiri.schema.json` on every launch, alongside the workflow schema, for YAML validation and autocomplete — map it the same way (modeline or `yaml.schemas`).
- **Workflows validate against it.** An `llm:` step's `model` is a `provider:model` id; the prefix must name a provider in this registry or the workflow fails to load — the same posture as a missing bundle.
- **Reloading.** Edits to `kiri.yaml` hot-reload while kiri runs, the same as `workflows/`. A valid change swaps the provider registry and re-validates workflows so `llm:` steps re-check their provider against the new set; an invalid edit is logged and the last-known-good providers are kept, so a mid-edit typo never breaks an in-flight session. Every settled reload — valid or not — publishes a `config.changed` event on the bus, so the in-app config-health panel and model picker refresh live as you edit (an invalid edit included, so a newly introduced error appears immediately).
- **Configuration health, surfaced not enforced.** Kiri reports configuration health rather than blocking on it — warn-and-continue, never failing boot. "Required" is contextual: an `sh:`/`use:`-only workspace needs no providers, so *no providers* is a degraded note, not an error; a declared provider whose API key is unset (including the conventional `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` fallback) is an error; an unparseable `kiri.yaml` is an error; a declared MCP server whose `{ env: }` ref is unset is an error, naming the server. The report is printed at startup and served at `GET /api/config/health`; the web app renders the non-ok checks as a banner atop the activity page (degraded as a warning, error as a problem). Per-provider model-listing failures from `GET /api/models` — a provider down or unauthorised — surface in the session model picker alongside the gap they explain.

### LLM step execution

An `llm:` step runs as a single non-streaming completion inside the kiri process — nothing is spawned. The runner renders the prompt template, calls the model through the provider registry, and maps the result onto the standard step envelope:

- **Prompt rendering.** Same `{{VAR}}` semantics as the script bundles' renderer (ASCII `[A-Z_][A-Z0-9_]*` names, one left-to-right pass, unknown names resolve to empty, substituted values never re-scanned), so existing bundle prompt templates port to `llm:` steps unchanged. The vars map is the step's env scope — its own `env:` (with refs resolved) plus the kiri-injected vars (`KIRI_RUN_ID`, `KIRI_STEP_INDEX`, `KIRI_REPO_ROOT`).
- **Envelope mapping.** The completion text becomes `output` and `traces.stdout`; `traces.stderr` stays empty — there is no second stream. Token counts from the response are persisted on `traces.usage` (input/output/total, fields omitted when the provider doesn't report them). A provider or API error fails the step with the provider's message; halt-on-failure semantics match every other step.
- **No file channels.** A completion can't read or write files, so llm steps are not offered `KIRI_RECOMMENDATIONS_FILE` and cannot declare `outputs:`. Upstream data reaches an llm step the same way it reaches any step — `{ step: <id> }` / `{ step, output }` / `{ article: <slug> }` env refs, resolved in-process into the prompt's `{{VAR}}` template vars.
- **Cancellation.** Cancelling a run aborts the in-flight HTTP request; the step and run finalise as `cancelled` through the same path as a killed child process.

Scope is completion-shaped steps: one prompt in, text out. Agentic work — tool use, multi-turn conversation — is **not** a workflow step: it lives in the separate agentic sessions pillar (see *Agentic sessions*). A workflow that wants a one-shot completion uses an `llm:` step; anything multi-turn or tool-driven is a session, not a step. (A `claude-code` script bundle remains a legitimate way to run an agent *inside a workflow step*, but that's a user-authored bundle, not kiri driving an agent loop.)

### Claude Code via the `claude-code` bundle

Kiri integrates with Claude Code through a `claude-code` script bundle — a worked example carried in the repo's `examples/` that the user copies into their workspace's `bundles/` and owns from then on. Kiri itself has no CC-specific code; the bundle does the spawning, config translation, transcript parsing, and meta emission. Spawning CC's CLI directly keeps Max subscription billing in play — the Agent SDK is API-billed only and not on the table for this personal tool.

Bundle layout (`examples/bundles/claude-code/`):

```
claude-code/
  run.sh         # spawns `claude` CLI with the rendered prompt
  README.md      # documents the env-var contract: PROMPT, PROMPT_FILE, MAX_TURNS, MODEL
```

Workflow usage:

```yaml
- use: claude-code
  env:
    PROMPT_FILE: prompts/pr-review.tpl
    MAX_TURNS: "50"
    MODEL: opus              # optional
```

What `run.sh` does at spawn time:

- Reads its env-var contract (`PROMPT` or `PROMPT_FILE` — `PROMPT` wins when both are set — plus `MAX_TURNS`, `MODEL`).
- Loads the prompt (`PROMPT_FILE` resolves against `KIRI_REPO_ROOT`) and renders `{{VAR}}` placeholders from the environment — env refs arrive as ordinary vars under the names the workflow gave them.
- Spawns `claude -p "$prompt" --max-turns "$MAX_TURNS"` (plus `--model` when set); its stdout/stderr land on kiri's standard step envelope.
- **Tool permissions defer to the user's own `~/.claude/settings.json`** — the bundle deliberately synthesises no settings of its own, which keeps it out of claude's credential-resolution path so the normal login flow keeps working. Constrain a workflow through prompt wording and your global claude config.

The bundle is plain bash — readable, modifiable, replaceable. The example lives in the repo; the user owns their copy from there.

### Output validation (for LLM steps producing structured output)

Three tiers, in order:

1. Use structured output / tool use at the API level. Kills ~95% of "wrapped in backticks" failures.
2. Validate against Zod schema. On failure, one-shot retry with the validation error fed back into the prompt.
3. *Optional* dedicated cleanup model — constrained to format-level repairs only. Stripping backticks: safe. Reshaping prose into fields: not safe.

### Cost tracking

First-party `llm:` steps persist token usage on their step row (`traces.usage`, straight off the provider response) — the numbers arrive without any side-channel, superseding the rationale for the retired `KIRI_META_FILE` meta channel where first-party calls are concerned. No cost/billing UI is built on top of them; the counts are simply kept.

Bundle-spawned agents (e.g. `claude-code`) still have no usage capture. The earlier design's generic meta channel (`KIRI_META_FILE` emitting `{ cost_usd, tokens_in, tokens_out, model }`) was retired unread to keep the runtime contract honest; if bundle-side numbers are ever wanted, that means re-introducing a transport plus UI promotion, with ccusage's transcript-parsing approach as the reference.

### Permissions philosophy

For agent-spawning workflow steps (the `claude-code` bundle), tool permissions come from the user's own global claude config (`~/.claude/settings.json`) — the bundle synthesises no per-step policy, and constraining a workflow is done through prompt wording and that config. Kiri itself adds no permission layer to workflow steps: **no runtime hooks for v1** — hooks are reserved for if/when dynamic per-call policy is wanted (token budget caps, mid-session escalation, tool-granular propose-to-approve). Per-call gating exists in the other pillar: agentic sessions approve tools per invocation (see *Agentic sessions → Tool permissions*).

Kiri does not wrap steps in a kernel sandbox: bundles are user-authored scripts in the user's own repo, with the same trust posture as any shell script they'd run themselves. If a bundle-install mechanism is ever added (a marketplace, `kiri install <bundle>`, etc.), revisit — the trust boundary changes at that point.

## Agentic sessions

The second pillar. Where a workflow is a fixed pipeline, an **agentic session** is a multi-turn conversation with a model that can reason, call tools, and stream its response. It is *not* built on the workflow engine and shares none of its execution model — only the surrounding infrastructure (config dir, SQLite, event bus, LLM provider registry) and the activity feed.

The pillar holds the **app-active and single-user invariants** unchanged: a session runs while the app is open, in-process, foreground, user-driven, and cancellable. A "running" session is an in-flight turn, exactly like a "running" run — there is no background agent, no overnight loop, no daemon turning the crank while the user is away.

### System prompt: core, `kiri.md`, project instructions, and the `AGENTS.md` chain

A session's behaviour is shaped by a layered system prompt, composed fresh on every turn from up to four layers, broadest scope first:

- **The kiri core layer** — immutable, authored by kiri itself. States the model's identity and the environment it runs in (a local-first, single-user tool; an interactive multi-turn chat; the current date, with a note that its training has a knowledge cutoff so it flags answers it can't verify). It carries the universal assistant baseline the core owns regardless of any `kiri.md` — lead with the answer, calibrate length and format, an honesty bar against fabrication (including the data behind a chart), and willingness to disagree. It states that replies render as GitHub-flavoured markdown with inline Vega-Lite `chart` blocks and `mermaid` diagrams (the same renderer workflow articles use) — a chart when the point is the numbers, a diagram when it's the structure, and neither for ordinary prose — and draws the trust boundary both ways: this prompt and the user's standing instructions are authoritative, while quoted file/web/tool/external text is untrusted data, not instructions. When the session has tools active it adds guidance to reach for them over guessing, parallelise independent calls, and treat a capped or timed-out result as incomplete — each tool carries its own name and description from its MCP server, so the core layer needn't enumerate them. Composed per turn rather than held as a constant because it states the live date and the active tool set.
- **`kiri.md`** — an optional workspace-root markdown file of standing instructions, applied to every session when present: the user's always-on "how I want sessions to behave."
- **Project instructions** — the container-scoped layer: optional markdown held on the project row (see *Projects*), carried by every session in that project and by no other. Authored in the app rather than in a file — the project is a database container, not a directory, so its instructions live with it and are edited from its page, or by a session in the project on request (see *Projects*) — and injected as one delimited block naming the project and its place in the gradient, so the model can tell it apart from the workspace and directory layers. Blank instructions are the same first-class "absent" as a missing `kiri.md`: the layer simply doesn't appear.
- **The `AGENTS.md` chain** — the directory-scoped layer, resolved against the session's **working directory** (see *Filesystem access*). `AGENTS.md` is the cross-tool convention for instructions that govern a directory and everything below it, so a session working in a repo picks that repo's conventions up with no kiri-specific setup — and unlike `kiri.md`, which is one always-on file for the whole workspace, the chain changes as the session moves. Assembly walks from the working directory up to the top of the tree collecting `AGENTS.md` paths and layers the surviving ones **most general first**, so the nearest file lands last and its directives win on conflict. Membership is decided by **realpath containment inside `filesystem.allowed_directories` before the file is opened**: a file above the sandbox is excluded without its bytes ever being read, and resolving first means neither a `..` in the working directory nor a symlinked `AGENTS.md` pointing outside can widen the boundary. That check is the whole security posture here — these reads carry no approval prompt (the read tools are `allow` by default), so nothing outside the declared sandbox may enter context. Absent, empty, and unreadable files contribute nothing, the same "absent" posture as a missing `kiri.md`.

Layers compose broadest first — **core → `kiri.md` → project instructions → the `AGENTS.md` chain** — each narrower than the last, so the more specific layer wins where two conflict. Every layer is resolved fresh each turn (the files re-read from disk, the project layer re-read from the database), so an edit takes effect on the next turn with git as the source of truth for the files; nothing is snapshotted. Reading per turn is also what keeps the chain honest across a `set_working_directory` move: the prompt is rebuilt against the session's stored working directory, so the next turn resolves the chain for where the session actually is. A missing `kiri.md` is a first-class default: the session runs on the core layer alone, a plain chat. A session with no working directory, or a workspace declaring no allowed directories, loads no chain — and kiri only ever reads `AGENTS.md`, never writes one. The one exception is a **child session** (see *Delegation*): identified by its parent link alone (there is no separate kind), it runs a focused, kiri-authored worker prompt in place of this stack — it is a delegated worker on a single task, not the user's chat, so none of the user layers — `kiri.md`, its project's instructions, the `AGENTS.md` chain — applies. The worker prompt keeps the capability guidance keyed off the child's active tool set (the sandbox roots, the shell rules), so a worker holding those tools still gets their contracts.

This deliberately replaces an earlier `agents/*.yaml` registry idea (a pre-baked definition bundling system prompt, model, tools, and params, snapshotted onto the session), and an interim persona system — per-session `personas/<name>.md` overlays injected after `kiri.md` — since removed: role overlays saw no use, and on-demand instruction packs (skills, see *Skills* below) are the better-shaped replacement. For a single-user tool, one always-on `kiri.md` covers standing behaviour without a registry or a per-session config snapshot. The model is chosen at session creation and swappable mid-conversation from the chat composer (alongside the effort level), applying from the next turn.

### Skills

A **skill** is a named instruction set the model pulls into the conversation on demand — the third point on the instruction spectrum: standing instructions (`kiri.md`, the `AGENTS.md` chain) are always-on, skills load when their task comes up, and workflows are executable. Skills live in the **config dir** — `skills/<name>/SKILL.md`, sibling of `workflows/`, committed and versioned like the rest of the config repo (explicitly not `.kiri/`, which is gitignored runtime state). The file is the standard SKILL.md shape: YAML frontmatter with `name` (defaulting to the directory name) and `description`, body = the instructions — and unknown frontmatter fields are ignored, so a skill written for another tool drops in unmodified. Supporting files can sit alongside `SKILL.md`; a session with the config dir in its filesystem sandbox reads them with the ordinary read tools.

The mechanism is progressive disclosure end to end: the system prompt lists each available skill as **name + one-line description only** (bodies are never inlined), and a single read-only `use_skill` built-in returns a skill's body when the model matches a task to one. Everything is read fresh — the catalogue per turn, the body per call — so an edit applies immediately, git the source of truth. First-party skills ship with kiri and are listed alongside the user's; the workflow-authoring reference is the first (generated per host rather than read from a file, so its shell rules match the machine). A user skill sharing a first-party name wins — their config, their instance. `use_skill` rides the standing tool-permission machinery on a default of `allow`, which means workers inherit it through delegation's allow-only rule: skills apply to delegated child sessions too, unlike `kiri.md`, which never did.

### Memories

A **memory** is a small durable fact carried across sessions — a preference, standing context, a correction — stored in a `memories` table in the workspace DB (kiri-produced data, like articles; explicitly not the config repo). One row per fact: a slug `name` the tools key off, a one-line `description` for indexing, a markdown body, an `updated_at` that surfaces fact age in curation, and a nullable `project_id` carrying the fact's **scope** — null for a workspace memory every session recalls, set for one only that project's sessions see. Names are unique per scope (partial unique indexes, mirroring articles' owner columns), so a project can hold its own `deploy-window` without colliding with the workspace's. Recall reuses the skills mechanism wholesale: the system prompt carries **name + one-line summary only** (alphabetical, so the index is byte-stable across turns and a save reorders nothing), and the body enters a conversation solely through `read_memory` when the model judges a listed memory relevant. The prompt section gates in two independent halves — the index renders when memories exist, the saving discipline (one fact per memory, save sparingly, update rather than duplicate, delete stale) renders when `save_memory` is active — so a fresh workspace still teaches the first save, and a read-only worker gets no instructions it can't act on. A project session carries **both indexes** — the workspace's and its project's, listed separately so the scopes stay legible — and a name held in both resolves project-first on read.

The tool surface is deliberately three verbs, not the articles' create/replace pair: **`save_memory` upserts by name** — a full replace when the name exists, a create when it doesn't, the result naming which branch ran. Articles are documents with a document lifecycle, where wholesale-replace vs targeted-edit is a real choice; a memory is one small fact with a "remember this" lifecycle, and forcing the model to classify the act as creation vs replacement would add a failure loop to exactly the action that must stay frictionless. All three tools default to `allow` — they only touch kiri's own database, and the **Memories page** (index plus per-memory read/edit/delete) is the standing trust surface in place of per-call prompts. The mutations are withheld from delegated workers (see *Delegation*); `read_memory` flows to them like any allow tool. **Writes stay in the session's own scope**: a project session's `save_memory` always writes a project memory — no scope parameter, since asking the model to classify a fact's reach reintroduces exactly the friction the upsert removes — and saving a name the workspace also holds saves alongside it rather than rewriting it. Deletion follows read: whichever scope resolved the name is the row that goes. Writes publish `memory.saved` / `memory.deleted` on the bus, carrying the project id for a scoped memory so each scope's caches refresh independently, and a REST surface serves the curation pages — `/api/memories` for the workspace's (list, read, patch, delete; no create endpoint, since saving is the model's job) and `/api/projects/:id/memories/:name` for a project's, its index riding the project detail payload beside the corpus. Memories are deliberately absent from the FTS index: the corpus is small by discipline, and the prompt index plus load-by-name *is* the recall mechanism.

### Storage

Two new tables alongside the existing four, following the runs/run_steps shape:

- **`sessions`** — one row per conversation: chosen model, status (`running` | `idle` | `failed` | `cancelled`), timestamps, a **running token total** (see *Usage* below), a nullable **title** — the display name the session list, feed, and search results lead with, set by kiri's own title generation off the session's opening message (see *Session titling* below) and editable by the user from the session page; untitled sessions fall back to their first user message (or short id) — and its **lineage** — a nullable `parent_session_id` (with the spawning `parent_tool_call_id`) marking a child session spawned by a parent's `delegate` call (see *Delegation*). The parent link alone distinguishes a delegated worker from a top-level chat — there is no separate kind. Deleting a session cascades to its children.
- **`messages`** — one row per message, child of `sessions`, ordered. Each message stores its role and an array of **AI SDK `UIMessage` parts** as JSON — text, tool-call, tool-result, file/image, reasoning. Per-message token usage rides on the row as JSON, mirroring `traces.usage`.

**Messages are stored as `UIMessage` parts, canonical and provider-agnostic** — this is the load-bearing early decision. Because parts already model tool calls and file/image attachments, adding tools and adding image uploads become *storage no-ops*: they are simply additional part types that were always persistable. Round-tripping to the model uses the SDK's `convertToModelMessages(history)`.

Large blob payloads (e.g. pasted image bytes) follow the same guidance as workflow traces: inline in SQLite to start, move to disk-backed blobs in `.kiri/` referenced by path only when payload size starts dragging feed queries. Decision deferred until it bites.

### Execution & streaming

A turn runs in-process against the provider registry — the same registry and `{ env: }` secret resolution as `llm:` steps — and is cancellable through the existing `CancelRegistry` (a turn, or a tool loop within a turn, is the cancellable unit). A turn is cancelled *only* by an explicit request (or swept to `failed` on restart): once started it runs to completion regardless of the client connection. Its streamed response is drained server-side, so navigating away, reloading, or dropping the connection leaves the turn running and persisting — a client returning mid-turn rejoins the live stream (see *Resuming* below) rather than the disconnect killing it. Two transports, each for what it is good at:

- **Per-turn token stream.** The turn endpoint returns the AI SDK's streamed response (`streamText(...).toUIMessageStreamResponse()`); the client renders tokens live via `@ai-sdk/react`'s `useChat`. The SDK owns the streaming protocol and the multi-step tool loop, which keeps kiri's bespoke surface small.
- **Coarse lifecycle on the existing SSE bus.** `session.*` events (started, turn added, idle, finished, deleted) ride the in-process event bus as thin cache-invalidation signals, exactly like `run.*`. **Token deltas do not go through this bus** — it is a status channel, and per-token fan-out is the wrong load for it.

**Resuming an in-flight turn.** The token stream is mirrored into an in-process registry, keyed by session, as it drains. A client returning to a running turn — a page refresh, or a second tab — reconnects through `GET /api/sessions/:id/stream`, which replays the frames buffered so far and then follows live, so `useChat` rebuilds the assistant message (text and tool-call state alike) and carries it to completion. The reconnect is fired once per session, so it survives the dev double-render without rejoining twice. The registry entry lives only as long as the turn — dropped the instant it settles, in step with persisting the message — so a client that has already loaded the settled turn from storage gets a `204` and never replays it into a duplicate. The registry is in-memory: a turn interrupted by a restart is swept to `failed`, not resumed.

On turn completion the new messages and their usage are persisted, and the session's running token total is updated.

### Tools

Tools are offered to a session's model through the AI SDK's tool loop. They are emphatically **not script bundles**: bundles are a workflow concept and the two pillars do not cross over. When a session has any tools, the turn runs as a **capped multi-step loop** — the model calls a tool, reads its result, and continues before answering — and the calls and results persist as `UIMessage` parts (a storage no-op, since messages were always stored as parts) and render in the transcript as a collapsed block showing what was called, with what, and its result (untrusted data, shown as formatted JSON — or, for a filesystem write, the change itself as a unified diff — never markdown). A run of consecutive calls — uninterrupted by prose — folds into a single collapsed panel summarising the count, the distinct tools, and a rolled-up status, expanding to the individual blocks; a call awaiting the user's approval never folds, its prompt staying in view.

A session's tools come from **MCP servers** the user declares under `mcp:` in `kiri.yaml`, keyed by name — a `stdio` server kiri spawns as a subprocess, or an `http` server it connects to over Streamable HTTP. An http server authenticates either with static request headers (e.g. `Authorization`) whose values are `{ env: }` refs, or — with `auth: oauth` — through an OAuth browser sign-in kiri runs on demand, persisting the tokens to `.kiri/mcp-credentials.json` (mode 0600, a file separate from the feed DB so secrets never touch queryable data). Those OAuth tokens are the one secret class that isn't an `{ env: }` ref; every other secret stays an env ref, never a literal. Kiri connects each server at boot and on `kiri.yaml` reload, discovers its tools, and offers them to the model **namespaced `<server>__<tool>`** so names never collide. Tools flow through `@ai-sdk/mcp`, whose client returns AI-SDK tools directly; an OAuth server's transport is swapped for the official `@modelcontextprotocol/sdk`'s Streamable-HTTP transport, whose OAuth resolves the discovery quirks of real servers (trailing-slash issuers, cross-host authorization servers) that `@ai-sdk/mcp`'s does not. This generalises the tool model's self-gating: a server's tools are offered only when it is configured and connects — a server whose declared env ref is unset, that fails to connect, or whose OAuth isn't signed in yet, is simply absent, the reason surfaced as a config-health check (an unsigned-in OAuth server as a one-click **Connect** prompt). The same holds once a server is running: a tool call that finds its OAuth expired and beyond refresh drops that server's tools and flips it back to the **Connect** prompt, rather than leaving it reported as connected while every later call fails. Configuring a server is the *first* trust decision — the same posture as reading a bundle before you `use:` it (and an MCP `stdio` server is arbitrary-subprocess-equivalent, so it warrants the same care) — but it is not the only gate: each individual tool call is approved before it runs (see *Tool permissions* below). The core system prompt frames tool output as untrusted data and gives a generic nudge to reach for the available tools; each MCP tool carries its own name and description from the server. Each call is bounded: its result is capped at 128 KB — truncated with a marker past that — so a large payload (a directory tree over a big folder, say) can't overrun the model's context or the provider's request-size limit, and it runs under a 180-second budget after which it is aborted and surfaced as a tool error the model can recover from. When a result carries a `structuredContent` object — the parsed payload an MCP server returns alongside the JSON text it also packs into `content` — kiri forwards just that object and drops the duplicate text, so the model isn't re-paid for both copies each time the result is replayed on a later turn; the 128 KB cap applies to the structured payload, falling back to the truncated text when it doesn't fit. An in-flight turn can be cancelled by pressing Escape — which stops the turn and marks any call in flight cancelled rather than leaving it on "working". Provider note: the OpenAI provider is wired to Chat Completions (`.chat()`), so tool-calling parity there is worth re-verifying as providers change. MCP servers provide the general catalogue — web search, for instance, is the Tavily MCP server plugged in like any other. Two first-party sets ride alongside. The **article tools** — `create_article`, `replace_article`, `edit_article`, `delete_article`, `list_articles`, `read_article` — are tools with a server-side execute against kiri's own database, scoped to the session's home: its own articles, or its project's shared corpus for a project session (see *Session articles* and *Projects* below). The **workflow tools** are the single sanctioned bridge to the workflow pillar: `list_workflows` serves each registered workflow's name, description, group, and declared inputs off the registry, and `run_workflow` validates the supplied inputs through the same schema as the invoke endpoint, starts the run through the ordinary runner (first-class: feed entry, live `run.*` events, cancellable from the run page), blocks until it settles, and returns a compact outcome — terminal status, per-phase statuses with any failing phase's error and the tails of its captured stdout/stderr (so the model can diagnose a failure without leaving the conversation), the summary, and the slugs of articles produced (readable back on request through `read_article` with the run id); success output stays on the run page. Aborting the turn requests cancellation of the run it started. `rerun_workflow` re-executes a settled run in place — the same wipe-and-reuse path as the run page's rerun, validated against the workflow's *current* definition — so the run keeps its id and feed entry, and a session repeating a run (above all the test-edit-test loop while authoring) evolves one entry instead of stacking near-duplicates; the system prompt, run_workflow's description, and the authoring guide all steer repeat executions through it. The authoring set — `read_workflow`, `create_workflow`, `edit_workflow`, `replace_workflow` — reads and writes the workflow YAML files themselves (see *Session-authored workflows* below): the first first-party tools that write to the workspace repo rather than kiri's database — with the deep authoring reference served on demand as the first-party `workflow-authoring` skill through **`use_skill`** (see *Skills* above). A third first-party set — the **filesystem tools** (see *Session filesystem access* below) — gives a session read and, per-call-approved, write access to the user's own files, opt-in via a declared sandbox in `kiri.yaml`. A fourth — **`generate_image`** (see *Session image generation* below) — renders text prompts with the image model selected on the session. A fifth — **`run_command`** (see *Session shell commands* below) — executes shell commands inside the same declared sandbox, starting from the session's working directory, opt-in and approved per call. A sixth — **`delegate`** (see *Delegation* below) — hands a self-contained task to a hidden child session that does the legwork in its own context and returns only a written report. A seventh — the **memory tools** (`save_memory`, `read_memory`, `delete_memory`; see *Memories* above) — saves, recalls, and deletes durable facts kept in kiri's database and indexed into the system prompt, scoped to the workspace or to the session's project. An eighth — **`update_project_instructions`** (see *Projects* below) — rewrites the standing instructions of the session's own project, and is offered only to a session inside one.
### Tool permissions

Configuring a server is the standing trust decision, but each tool also carries a **standing permission** — `allow`, `ask` (the default), or `off`, plus `auto` on the shell tool alone (a per-call judgement between running and asking; see *Session shell commands*) — that governs every invocation. An `ask` tool pauses the turn when the model calls it and the transcript shows an **Allow / Always allow / Deny** prompt with the call's input, so nothing runs on the user's behalf without consent. Allow runs the call once; Deny refuses it and tells the model so (with a standing reason, so a model doesn't loop re-requesting the same call); Always allow runs it and flips the tool's permission to `allow` so it never prompts again. An `allow` tool runs straight through without a prompt; an `off` tool is withheld from the model entirely — never offered, so it can't be called and never prompts. Allow-once and Deny don't persist; the `allow` and `off` permissions do.

This is built on the AI SDK's native tool-approval flow rather than a bespoke channel. Each MCP tool is offered with a `needsApproval` predicate; when it returns true the SDK stops the loop and streams a tool-approval request over the same `UIMessage` stream the transcript already consumes, the call persisting as an `approval-requested` part (a storage no-op). The client renders the three choices and replies with `addToolApprovalResponse`, which resubmits the turn to resume it: the SDK runs the allowed call (or feeds back the denial) and the model continues, extending the same assistant message in place. Pausing leaves the session `idle`, so a decision survives a reload — the prompt is re-rendered from the persisted part — and a new message can't be sent until the pending call is resolved.

Permissions are keyed by the tool's namespaced `<server>__<tool>` name — arguments are not part of the key; the shell tool's `auto` mode is the one argument-*sensitive* permission, but what varies per call is the runtime verdict, never the stored entry, which stays plain `auto` by tool name — and persist in a gitignored **`.kiri/tool-permissions.json`**: every recorded verdict is stored (`allow`, `ask`, or `off`), an absent entry reading back as the tool's default — `ask` for MCP tools, a built-in tool's own declared default (see below). The file is read on every tool request so a decision is honoured across sessions and restarts, and a hand-edit takes effect on the next turn with no restart. Writing a permission through the page publishes a `tool.permission.updated` event, so a second open tool listing reflects the change rather than serving its cache; a hand-edit of the file publishes nothing, so an already-open page shows it only after a reload (it still applies to the next turn either way). Unlike `mcp-credentials.json` it is plain JSON with default permissions — tool names are not secrets. The **Tools & MCP page** (`/mcp`) is the surface for reviewing and changing these: it lists each configured server, its connection state (with the same Connect prompt for an unsigned-in OAuth server), and its tools, each with an Always allow / Ask / Off control — the inline prompt's Always allow is just a shortcut that writes the same `allow`. One subtlety the SDK forces: it re-checks `needsApproval` when resuming and denies a call that no longer needs approval, so a tool flipped to `allow` mid-turn still reports as needing approval for a call the user has *already* answered this turn — the new permission takes effect from the next fresh call, not by cancelling the one in flight.

First-party tools ride this same machinery; what differs per tool is only the default. Every built-in session tool is declared in one registry (`BUILTIN_TOOLS`) carrying its management-surface blurb and its **default permission**: tools that only read kiri's data or write inside its database — the article tools, the memory tools (whose standing oversight is the Memories page), `list_workflows`, `read_workflow`, and `use_skill` — default to `allow` (the request in chat is the authorisation, so a prompt would add friction without trust), as do the filesystem read tools, whose reach is the `filesystem.allowed_directories` sandbox the user declared in `kiri.yaml` (declaring it is the authorisation; see *Session filesystem access*), and `generate_image`, which runs against the image model the user selected on the session (selecting it is the authorisation; see *Session image generation*), and `delegate`, whose worker holds only standing-allow tools so delegation never widens what runs unprompted (see *Delegation*), while `run_workflow` and `rerun_workflow` execute user-authored scripts, the workflow write tools (`create_workflow`, `edit_workflow`, `replace_workflow`) put runnable automation into the workspace repo, the filesystem write tools (`write_file`, `edit_file`, `create_directory`, `delete_file`, `delete_directory`) change the user's own files, and `run_command` executes model-authored shell commands, so they default to `ask` — the sandbox authorises reading, but each mutation still gets a human decision. A tool whose capability isn't configured — the filesystem tools and `run_command` with no usable sandbox — is withheld regardless of its permission, as is `delegate` from a child session: a worker can't spawn workers. Built-in permissions are keyed by the tool's plain (un-namespaced) name, and built-ins are merged after the gated MCP set so a name collision resolves to the first-party tool. The Tools & MCP page lists every built-in under a **Built-in tools** card (collapsed by default — the tools sit on sensible defaults) with the same Always allow / Ask / Off control, so any default can be reviewed and overridden — including setting an `allow`-default tool back to asking, which is why the store persists an explicit `ask` rather than treating absence as one. An `off` built-in is withheld from the model like any other tool, and the system-prompt guidance keyed off it drops out with it.

### Session articles

Sessions produce articles through the first-party article tools, writing the same `articles` table as workflow runs via the `sessionId` producer column (the XOR groundwork now exercised; deleting a session cascades its articles with its messages). `create_article` and `replace_article` take a full markdown body — create rejects a slug the session already used, replace optionally renames — while `edit_article` is a targeted exact-string replacement: `old_string` must match the current body exactly and appear once unless `replace_all` is set. Expected failures (unknown slug, duplicate slug, ambiguous or missing match) throw with a message naming the recovering call, surfaced to the model as a tool error so it self-corrects mid-turn; slugs validate against the same schema as workflow article slugs, and tool results carry compact metadata, never the body. `delete_article` removes one permanently — publishing `article.deleted`, mirrored by a delete action on the article pages themselves; run articles alone stay immutable. `read_article` additionally takes an optional run id to read an article a workflow run produced — the read-back half of the `run_workflow` bridge. When the tools are offered, the core prompt adds an article-guidance layer: the deliverable goes in the article and the reply stays a pointer, targeted edits are preferred over wholesale rewrites, and freshly written content isn't re-read. The turn-step cap is sized generously (32 round-trips) so a long edit pass fits in one turn. A session created inside a project points these same tools — same names, same permissions — at the project's shared corpus instead (see *Projects* below).

Every write publishes a thin `article.written` event, bridged to the query cache from the root like every other resource — so the session rail's articles panel, the session's feed rows, and an open article page all repaint live, and a page that isn't mounted goes stale and refetches on return rather than serving the old body. Session articles read back through `GET /api/sessions/:id/articles` (list, heading projections only) and `/:slug` (full body), and render at `/sessions/:id/articles/:slug` through the same reading view as run articles, situated under their session. Session rows in the activity feed and sessions tab carry their articles in the same indented block run rows use. The edit tool makes session articles the one mutable article class — run articles stay immutable once written.

### Projects

A **project** is the third article owner: `articles` carries a `project_id` column completing a strict three-way XOR with `run_id` and `session_id` (exactly one owner, enforced by the rebuilt check constraint — the SQLite table-rebuild dance again, this time also recreating the FTS triggers the rebuild silently drops), and `sessions` carries a nullable `project_id` set at creation and never moved — a session is born into a project (the create endpoint validates the project exists) or lives without one, and delegated children inherit their parent's. The shape encodes the design decision: **ownership never transfers**. The explored alternative — a global knowledge corpus with named sources and per-article opt-in — was rejected as curated-by-nobody and consumed-by-everybody; scoping the corpus to a project makes creating a session inside it the curation act, and the deliberate absence of promote/demote/attach flows keeps the invariant one line: run XOR session XOR project, set at insert. (Post-hoc session assignment and article promotion are recorded future doors, not v1.)

A project session's article tools are the same six verbs with the owner filter swapped: they read, write, and delete the project's shared corpus — any of the project's sessions edits any article whoever wrote it, slugs unique per project — while a projectless session's stay scoped to itself, the tool copy stating whichever scope is live. The prompt carries a project layer on the memories-index pattern: the container's name and the corpus index as slug-and-title lines (title = the body's first heading, name fallback), bodies entering the conversation only through `read_article`; a curation line — write durable knowledge into the corpus, improve articles other sessions wrote, cross-link with `[[slug]]` — renders only when the write tools ride, so a read-only worker gets the map alone. Retrieval stays **map-in-prompt + read-on-demand** by design: a curated corpus is small, and the heading-chunked per-project FTS design from the exploration is recorded for the day one outgrows it. `[[slug]]` references render as links through a remark plugin resolving against the corpus index — in the project reading view and in a project session's chat feed, where the model cross-references articles in its replies. Text nodes only, so code spans keep the syntax literally, and a slug nothing owns stays as written rather than linking to a 404; every other markdown surface (including a projectless session's chat, which has no corpus) leaves the syntax untouched.

Deleting a project cascades the whole container in one transaction — its corpus, its memories, its sessions, their delegate children, and everything those sessions own — announcing each cascaded top-level session so live feeds drop them, with the confirm stating real counts. Freshness rides `project.*` events plus owner-tagged `article.written` / `article.deleted` payloads; session lifecycle events carry no project id, so they restale every project query wholesale rather than none. Search needed only a projection widening — the FTS triggers are owner-agnostic, so a corpus article indexes like any other and its hit routes to the project reading view. The feed reaches the corpus only through the Articles view (see *Activity feed*): a project session's row can't list articles it doesn't own, so the project is what the timeline attributes them to. A project also owns **memories** (see *Memories* above): its sessions save durable facts into the project's scope rather than the workspace's, the project page curates them with the same read/edit/delete affordances as the global page, and the cascade takes them with the container. A project also carries its own **standing instructions** — a nullable `instructions` column on `projects`, edited from the project page in a wide modal and layered into every session in the project (see *System prompt* above) — the container-scoped point of the standing-instructions gradient, and the reason it lives in the database rather than as a `project.md`: a project has no directory to hold one. A project session can also rewrite them in conversation with **`update_project_instructions`**, the one first-party tool that edits a standing-instruction layer. It is wholesale-replace with no read counterpart — the current instructions are already in the session's own prompt — and defaults to `allow`, because the guard against unwanted edits is not a prompt but the pairing of emphatic tool-description steering (call it *only* on an explicit request; a preference expressed in passing belongs in a memory or the reply) with the unified diff its result carries into the transcript, rendered by the same pipeline as the filesystem write tools and stripped before the model is re-paid for it. Withheld from delegated workers alongside the other write tools: a worker doesn't even carry the layer, and the standing record is the user-facing conversation's to change. Recorded future directions beyond retrieval: per-project disk mounts.

### Session-authored workflows

Sessions author workflows through four write-capable tools — `read_workflow` returns a file's raw YAML by workflow name (the registry carries each definition's source path for exactly this), `create_workflow` writes `workflows/<slug>.yaml`, `edit_workflow` makes an exact-string replacement mirroring `edit_article`, and `replace_workflow` rewrites a file wholesale. The interface is **whole YAML file content**, deliberately: mirroring the step/env discriminated unions into a structured tool inputSchema would duplicate `workflowSchema`, degrade tool-call reliability, and a structured→YAML renderer couldn't preserve comments or formatting on edit. Everything structured input would have guaranteed is recovered by the validation gate instead: every write runs `parseWorkflowSource` — the loader's own per-file pipeline (YAML parse, schema, bundle existence, llm provider names via the live registry, prompt files) — and an invalid source throws the gate's reason back as a recoverable tool error, so nothing invalid ever reaches disk. Duplicate workflow names and filenames are rejected pre-write, as is a rename (the name lives in the YAML) that collides with another workflow. Writes land in the watched directory, so the catalog and registry pick them up through the ordinary watcher rebuild without a restart — registry lookups can lag a write by the debounce (~50ms), immaterial at model-turn speed.

The model is taught to author through **progressive disclosure** rather than the system prompt: the first-party `workflow-authoring` skill returns the full authoring reference (file shape, step kinds, data-flow and env rules, articles/summarize, working method — distilled from the workspace authoring reference, scoped to what a session can do), and each write tool's description says to load it with `use_skill` once per conversation before authoring. Sessions that never author pay only the tool descriptions. This began life as a dedicated `read_workflow_authoring_guide` tool — a skill in disguise — retired when generic skill support landed (see *Skills* above) with the guide content as the first first-party skill. Model selection is ask-first: the guide forbids inventing a `provider:model`, sending the model to the user's standing `kiri.md` preferences, then an existing workflow's choice, then a question to the user — and an unknown-provider rejection names the configured set. Out of scope, deliberately: authoring bundles or prompt template files (sessions have no tools for them; the guide steers to inline prompts and existing bundles), and deleting workflows.

### Session filesystem access

Sessions read the user's files through four first-party tools — `find_files` (glob), `list_directory` (one level, directories marked with a trailing slash), `read_file`, and `search_files` (per-line regex with an optional include glob) — confined to a declarative sandbox: the `filesystem: allowed_directories` section of `kiri.yaml`, entries workspace-root-relative (`"."` grants the root, a leading `~` expands to the home directory), resolved to absolute paths at load. **Declaring the sandbox is what enables the tools**: with no section — or none of its directories existing on disk — the set is withheld from the model entirely, the same self-gating as an unconfigured MCP server, and a failed config load empties the sandbox rather than defaulting it (fail closed). Results report real absolute paths; a model-supplied path may be absolute or relative, a relative one resolving against the **session's working directory** — a per-session value seeded at create from `filesystem.default_working_directory` (validated at config load to sit inside the sandbox; the first allowed directory when unset), inherited by delegated child sessions, and moved only through the `set_working_directory` tool, whose argument clears the same realpath-and-containment guard as every other path (the tool defaults to `allow`: it only repoints a value that is itself confined). The stored directory is re-validated against the live sandbox before each turn: a turn whose directory has left the disk or the sandbox refuses to play — announcing the problem and clearing the stale value in the same stroke, so the *next* message self-heals from the configured default (a session with no working directory picks the live default up whenever it is next loaded; there is no manual reset, and nothing app-side ever writes a path) — rather than silently operating somewhere else, and with no sandbox declared the check stands down, since the tools it protects are withheld anyway. Every model-supplied path is resolved to its real form, defeating `../` traversal and symlink escapes, and must land inside a declared directory; hidden (dot-prefixed) paths are reachable like any other, bar a narrow denylist that stays outside the surface outright — never listed, searched, or readable: `.git` internals (thousands of object files that would drown every broad find) and secret-bearing files (`.env*`, `.kiri/mcp-credentials.json`), because reads run unprompted and a secret must never enter the transcript or the feed DB. Reads of binary files are refused, oversized results are truncated or capped with a note naming the recovery, and expected failures throw messages naming the recovering call. The broad walks (`find_files`, `search_files`) are built to survive a huge sandbox: they walk asynchronously — yielding to the event loop per directory, so a walk can never freeze the server the way a synchronous scan would — prune dependency, cache, and build-output directories wholesale (`node_modules`, `dist`, `build`, `target`, `.venv`, and kin — conventionally-generated names only, and never files sharing those names) unless the call names one (in the pattern/include, or via a `directory` inside one), and stop at a scanned-entry budget with a note telling the model to narrow its scope. When the tools are offered, a core-prompt guidance layer enumerates the reachable roots and states the path currency (absolute results; relative inputs against the working directory), the prompt intro states the working directory as of each turn's start — stable turn over turn until a move, so prompt-prefix caching only re-reads after one — and the model is steered to move only when the root of the work changes, never to reach a subdirectory relative paths already cover; it all drops out with the tools, each half (read discipline, the write contract) keyed off its own tools being offered. The read tools default to `allow` — the declared sandbox is the authorisation (see *Tool permissions*).

Five mutating tools share the same sandbox and containment guard: `write_file` (create or overwrite, missing parents created, trailing newline normalised), `edit_file` (exact-string replacement mirroring `edit_workflow` — old text must match uniquely, or `replace_all`), `create_directory`, `delete_file`, and `delete_directory` (empty only, unless `recursive` — and never an allowed root itself). A path that doesn't exist yet is confined through its nearest existing ancestor and the full target re-checked, so `../` traversal, symlink escapes, and denylisted segments are rejected before anything touches disk; a broken symlink is refused rather than written through; binary files are refused for writing and editing as they are for reading. Every mutating tool defaults to `ask`.

An overwrite or edit returns a **unified diff** of the change alongside its compact metadata. The diff is app-only payload: the transcript renders it as the call's result (a created file's content renders as additions rebuilt from the input), and the approval prompt previews the change the same way before the user decides — but the model never receives it. Inside the running turn the tool's `toModelOutput` swaps in the diff-less metadata, and on every later turn a send-time history transform (a sibling of the TOON re-encode, run before it) strips it from what is sent — the change is already carried by the call's own input, so re-sending it would only re-pay tokens. Diffs are capped and flagged when truncated, and persisted messages keep them, so the transcript's rendering survives reloads.

### Session shell commands

Sessions run shell commands through a first-party **`run_command`** tool — the command executed via `bash -c` (model-authored scripts assume bash; `sh`'s POSIX-mode differences would be silent bugs) in a working directory confined to the same `filesystem.allowed_directories` sandbox as the file tools — **declaring the sandbox is what enables the tool**; absent, or with no declared directory existing on disk, `run_command` is withheld entirely. Its confinement is deliberately narrower than the filesystem tools', and stated honestly everywhere it's described: only the *working directory* is checked (resolved through symlinks, subdirectories allowed; an omitted `cwd` is the session's working directory — falling back to the sole allowed directory when the session has none — and a relative `cwd` resolves against it, so a command never silently runs in the wrong project) — what the command itself touches is not confinable, which is exactly why the tool defaults to `ask`: every call pauses with the command previewed verbatim, and that per-call approval — not the directory list — is the security boundary. There is no path denylist here: that rule protects the filesystem tools' pre-authorised reads, and nothing here runs unseen.

Execution mirrors the workflow runner's spawn with three deliberate differences: bash rather than `sh` (above), the kiri process env inherited rather than scoped — PATH, HOME, and the user's tooling setup are the point of interactive, per-approved work, unlike a reproducible workflow step — and SIGKILL on timeout or cancel, because a trappable signal could hang the turn. Commands run non-interactively (stdin reads end-of-file), are killed at their timeout (default 120 s, capped at 600), and die with the turn on cancel — nothing outlives it, holding the no-daemons invariant. A non-zero exit is a *result* the model reads — exit code, stdout, and stderr, each stream tail-capped and flagged when cut — not a tool error; only a call that can't start (bad cwd, nothing configured) throws, naming what recovers. The transcript renders a settled call as its exit status and output streams, and the approval prompt shows the command in a code block with its directory. When the tool is offered, a core-prompt guidance layer enumerates the sandbox, states that commands run in the session's working directory, and carries the command-safety contract as hard prohibitions — propose only commands safe to run unattended, nothing destructive beyond the named need, no escalation, no secret-printing, no fetch-and-execute — the first line of defence in front of the approval gate.

An opt-in **`auto` permission** — the shell tool is the only tool that offers it — moves the run-or-ask decision per command, so routine calls (`git status`, a test run) stop prompting without granting blanket `allow` to a tool whose reach is everything the user can touch. The decision layers deterministic-first: a screen strips shell comments (text hidden in a comment never reaches a judgement), hard-asks on triggers no judgement may override (`sudo`, recursive deletes, history rewrites and force-pushes, piping into a shell, decode-and-run obfuscation, nested `sh -c`), and always-allows only an exact, metacharacter-free list of read-only commands. Everything between goes to a single **utility-model judgement** (`models.utility` — deliberately *not* the session's model, which must not approve its own commands, and unlike titling there is no session-model fallback: with no utility model configured, `auto` degrades to `ask` wholesale, screen included, so the permissions page can state the fallback plainly) that receives only the sanitised command and its directory — never conversation content — states the command's effects before its verdict, and fails closed on every path: provider error, timeout, an unreadable reply, an over-long command, all resolve to asking. An `ask` outcome lands in the ordinary approval prompt; every decision is logged with its reason so unprompted runs stay auditable. `auto` is a convenience layer over the approval boundary, not a second boundary: its worst case is exactly `ask`, and delegated workers treat it as such — an `auto` tool is absent from a worker like any non-`allow` tool.

### Session image generation

Sessions generate images through a first-party `generate_image` tool, gated on a per-session **image model**: a nullable `imageModel` column on the session row, picked in the chat composer's model group from the image-output models the providers offer, cleared with **None**. Selection is the whole gate — the tool is offered only while an image model is set (the same self-gating as an unconfigured MCP server or an undeclared filesystem sandbox), re-reads the selection on every call, and defaults to `allow`: selecting the model is the authorisation, and a generation is a provider-billed model call like any turn.

Knowing which models generate images is a classification concern of the model listing: `GET /api/models` classifies every entry by what it produces — `text` or `image` — reading whichever shape the provider exposes, strongest first: `architecture.output_modalities` or the arrow-form `modality` string (OpenRouter-shaped listings), `metadata.tags` (DeepInfra), a Together-style `type` tag (Anthropic's `type: "model"` is no signal and falls through), Mistral-style `capabilities.completion_chat`, then well-known id families for bare listings (OpenAI, and Google's or xAI's OpenAI-compatible endpoints, which name image models by id alone). Image wins over text — a model that can emit both exists to generate images — and a model producing neither (audio, video, embeddings) is dropped from the listing outright: nothing in kiri can drive it. The session model picker offers only `text` models, the image-model picker only `image` ones, and router pseudo-models (`openrouter/auto`) report an image modality but are used as chat models, so they stay `text`. The listing answers a second, sparser question the same way — whether a model *accepts* image input — reading `architecture.input_modalities` or the arrow form's left-hand side, Anthropic's `capabilities.image_input.supported`, Mistral's `capabilities.vision`, or a DeepInfra `vlm` tag / Together-style `vlm` type; a bare listing (OpenAI) says nothing, so `imageInput` stays unset — unknown, never guessed false. The session aside notes the selected model's answer under the picker whenever one is known, so it's visible before attaching an image.

Generation resolves the `provider:model` id through the same registry as chat (`resolveImageModel`), building an AI SDK image model against the provider's OpenAI-style `/images/generations` endpoint — OpenRouter and other gateways serve it alongside chat completions; an `anthropic` provider offers no image generation and refuses. The result rides the tool part as a **data URL** — inline in SQLite per the blob guidance above — and the transcript renders it at up to the container's full width with a full-resolution modal preview, standing alone outside any folded tool chain: it is content, like prose, never plumbing to fold away. The model itself never receives the bytes — `toModelOutput` hands back compact metadata in-turn, and a send-time history strip (a sibling of the filesystem diff strip) drops the payload from every later turn — so a generation costs its call once and never re-pays context.

### Delegation

Sessions delegate through the first-party **`delegate`** tool — a way to hand off a self-contained task (multi-step web research, above all) without filling the conversation with it. The work runs as a **child session**: the tool's server-side `execute` get-or-creates a real, full session — marked by `parent_session_id` and the spawning `parent_tool_call_id`, idempotent on that call, running the parent's model — and drives it through the ordinary turn loop entirely server-side, with the model's `task` as its one user message. The child cannot see the parent conversation — the task is its entire brief — and runs the focused worker prompt (see *System prompt*) with its own context window and step budget. Only the worker's final text crosses back, as the tool's result: the parent's context holds the findings, not the intermediate searches. That rollup is the whole point, and the core tool guidance steers the model to delegate multi-step research rather than search inline — and, the other way, not to re-run the searches a report already covers.

The trust posture is one invariant: **delegation never widens what runs unprompted.** A worker runs unattended — no approval prompt can surface mid-delegation — so it holds the parent catalogue narrowed to tools whose standing permission is `allow`, offered ungated; an `ask` tool is simply absent from a worker, and so is an `auto` one — its judgement can ask, and a worker has no one to ask. Withheld regardless of permission are `delegate` itself (a worker can't spawn workers), the article write tools (a worker's deliverable is its report; articles it wrote would ride a hidden session), and the memory write tools (curating the durable record stays with the user-facing conversation; `read_memory` flows to workers like any allow tool). `delegate` itself defaults to `allow` for exactly this reason — the trust gates are the standing permissions its worker inherits — and rides `BUILTIN_TOOLS` like any built-in, so the Tools & MCP page can flip it to ask or off. Forwarding a child's approval requests to the parent transcript — which would let workers hold `ask` tools under live supervision — is a deliberate later step, not v1.

A child is **hidden from the feed, the session list, and search** (the list and feed filter to top-level `parent_session_id IS NULL` rows; the FTS message triggers skip child transcripts at index time) yet first-class — reachable at its own `/sessions/:id` URL, streaming through the same resumable-stream registry, cancellable through the same endpoint, and accepting user-driven follow-up turns on its own page, where it keeps the worker prompt and is gated like any session (approvals work there; a human is present). The parent transcript renders the call as an **embedded child-session box**, found through `GET /api/sessions/:id/children` and matched on the spawning call id: collapsed to the task and the child's live status, expanding to the worker's transcript (prose and inner tool calls), a link to the child's page, and a cancel that aborts just the delegated task — the tool resolves with a cancelled note and the parent model carries on, distinct from cancelling the whole parent turn, which cascades into the child. A failed or report-less child likewise resolves to a note rather than an error, so the parent never hangs on a delegation.

### Session titling

A new session names itself without model cooperation: as the first user message starts its turn, the server fires a **one-off text generation** — not awaited by the turn — that titles the session from that opening message, publishing `session.updated` so the list and feed pick the name up while the reply is still streaming. The call runs against the **utility model** (`models.utility` in `kiri.yaml`, a `provider:model` reference resolved at use like a shortcut or delegate), the knob for kiri's own small internal generations; unset, it falls back to the session's model, so titling works with zero configuration and the utility model is purely a cost/locality optimisation (a small local model fits it well). The shell tool's `auto` judgement runs on this same knob but with the opposite fallback posture — no utility model, no judgement, `auto` asks (see *Session shell commands*): a title is cosmetic, a command decision is not, and the session model must never approve its own commands. The design is deliberately not a tool or a prompt steer: an instruction-driven title depends on the model following through (unreliable in practice) and lands only as the turn ends, and keying the system prompt off the titled state rewrites the prompt's first block after turn one — a full prompt-cache invalidation. Server-side generation is deterministic, immediate, and keeps the system prompt static. The generation fires once, on the first message of an untitled session only — a failed call (logged, never surfaced to the turn) leaves the session on its untitled fallback rather than retrying, and a title the user set while the call was in flight is never overwritten. The user renames or clears the title from the session page; a child session, hidden from every list, is never titled.

### Usage & context

Sessions deliberately diverge from the workflow pillar's "usage lives only in per-step traces" stance (a dedicated usage column was once dropped there for lack of a reader). An agent loop genuinely needs **budget visibility** — cumulative input/output tokens and proximity to the model's context window, surfaced on every turn and likely on the feed row. So sessions keep **both** per-message usage *and* a denormalised running total on the `sessions` row, justified by that concrete read pattern. The **context window** itself isn't stored — it's read live from the provider's model listing, the same `GET /api/models` the picker uses. Anthropic, OpenRouter, vLLM, and DeepInfra report it inline (DeepInfra nested under each entry's `metadata`); LM Studio reports it only on its native `/api/v0/models`, probed best-effort when the OpenAI-compatible listing comes up short; OpenAI reports nothing, so those models have no known window. The session aside shows the current fill as `current / limit` when the window is known, and a warning surfaces as the conversation nears it. That fill is the last settled turn's **context footprint** — the tokens of its final model call alone (the input it sent plus the reply it produced), recorded per turn alongside the summed spend. A tool-using turn is several model calls, so the cumulative usage sums each call's input and over-states what any single request sent; the footprint is the true high-water mark, and a turn that records none shows no fill until the next settles. Long-running context management begins here with **tool-result culling**: once the last settled turn's fill is over 80% of the known window, the history sent to the model keeps the three most recent tool results in full and replaces older ones with a short notice, each call's invocation left intact so the model still sees what it ran. The late trigger keeps culling a last-resort valve rather than a routine degradation, and delegate results are exempt — a worker's report is distilled findings that can't be cheaply or reproducibly re-run, so it survives every cull without spending one of the three kept slots. It's a send-time transform over the turn's outbound messages — the stored messages and the transcript are untouched — and it no-ops when the window is unknown (OpenAI) or no turn has settled yet. The per-turn check reads the window through a short-lived cache of the model listing rather than refetching each turn. Riding alongside culling is a second send-time transform: every surviving tool result whose output is JSON is re-encoded as TOON (Token-Oriented Object Notation) wherever that is the smaller, lossless form — the choice made per result, so it never enlarges one, and applied every turn rather than only over budget. The win is structural and so workload-dependent: a uniform array of short-field records collapses to a header naming its fields plus one comma-separated row each (TOON's sweet spot), while prose-heavy output barely moves. Encoding is the `@toon-format/toon` library, lossless by design (covered by a round-trip test) so a re-encoded result decodes back to exactly the original JSON; the stored messages stay JSON, and the core prompt briefly tells the model some results arrive as TOON so it reads them as the data they represent. Fuller management (summarisation, sliding windows) as a conversation outgrows the window remains its own concern, deferred.

### Activity feed

Sessions are activity and belong in the feed. The home feed is a polymorphic union over `runs` + `sessions`, newest-first by `startedAt` with a composite `(startedAt, id)` cursor, fronted by an `All · Articles · Runs · Sessions` tab strip, where `Runs` and `Sessions` filter the union by kind. The tabs name the events they list, not the workflow definitions behind them; the catalogue in the nav is a separate surface. The filtered tabs reuse the per-kind `runs` and `sessions` feeds, so only the union carries the composite cursor. **Articles** is a different query rather than a filter of that union, served by `GET /api/activity/articles` — a plain keyset page over `articles` ordered by `(created_at, id)`, since one table needs no merge — projecting each row's owner as `{ kind, id, label }` (a run's workflow name, a session's title/opening-message/short-id, a project's name) and leaving path construction to the client. It is the only feed a **project's** corpus reaches: those articles are owned by the project rather than by whichever of its sessions wrote or last edited them, so no session row can honestly carry them. Unlike the run and session feeds it does *not* filter out delegated children's work — an article a worker wrote is still a document, and the view's promise is everything kiri has written. **Child** sessions are excluded from every feed, the session list, and search — the queries filter to top-level `parent_session_id IS NULL` rows and the FTS triggers skip child transcripts — since a delegation is part of its parent's turn, not standalone activity; it surfaces inline in the parent and at its own URL (see *Delegation*).

## UI

- **Left rail: navigation.** `Activity` (the home feed), `Workflows` (the catalog), a one-click **+ New session** action, then the documentation links and version footer. Below the `lg` breakpoint the rail collapses to a top bar (wordmark + menu button) that opens the same nav in a left drawer.
- **Center: blended activity feed.** A reverse-chronological log of both workflow runs and agentic sessions, interleaved newest-first and day-grouped, behind an `All · Articles · Runs · Sessions` tab strip (deep-linked via `?view=`). Every row's byline leads with an accent kind marker — `run`, `session`, `article` — so a mixed feed reads down one column of entity nouns. A run row's byline shows that marker, status, relative start, duration, and a small count when it carries recommendations; below it the row's headline links through to the run, the way a session row's title links to its chat. A run has no name of its own, so what titles it depends on where it is read: the **workflow** in the blended feed, where that is what you scan for, and **when it ran** on a single workflow's page, where every row would otherwise carry the same headline. Its id titles it nowhere — an id addresses a run, it doesn't name one. Below the headline sit the run's one-or-two-sentence summary, when present, then the articles it produced — indented past the headline and opened by a faint count (`2 articles`): a row's headline and its articles are both standalone display-face links, so without that containment a row reads as several peer titles rather than as one entry and its output. Each article carries the body's first markdown `# heading`, falling back to its name, so identically-named articles from the same workflow are distinguishable. A session row is differentiated as a conversation, not an artifact record: an accent `session` kind marker leads its byline (status, model, relative start), and its title — when one is set — leads the row, upright and unquoted like a run headline; an untitled session's first message renders as quoted speech instead — italic display face between accent quotation marks — and before a title or message exists the short id stands in, unquoted. (Turn counts and token totals stay on the session page; the list API doesn't carry them.) Clicking a run row opens the run detail page (`/runs/:id`) with full traces, the run's recommendations, and its articles; a session row opens its chat (`/sessions/:id`); an article entry opens its dedicated page, nested under whichever container owns it (`/runs/:id/articles/:slug`, `/sessions/:id/articles/:slug`, `/projects/:id/articles/:slug`). An article row on the Articles tab has no lifecycle to report, so it takes an accent left edge where run and session rows take a status colour — marking it as something the system produced rather than something it did — and its byline names the container it lives in.
- **Run detail (`/runs/:id`).** An eyebrow naming the kind alone (`Run`), then *when the run ran* as the page heading — the breadcrumb above already names the workflow, as a link, so an eyebrow echoing it would read as the same string twice; the heading's job is to say which run, and the only fact separating two runs of one workflow is when each happened. The run's id is an address rather than a name, so it stays out of the heading and breadcrumb entirely.
- **Search (box above the feed tabs, or ⌘K/Ctrl+K anywhere).** A modal overlay over an autofocused query box: results load as you type (debounced), grouped `Articles · Sessions · Runs · Workflows` with the matched terms highlighted in a snippet; ↑/↓ walk the results from the box, Enter or a click opens one. Backed by a single FTS5 table (`search_fts`, `porter unicode61` tokenizer) that SQL triggers keep in step with its sources — article names and bodies, session titles and the text parts of user/assistant session messages (reasoning and tool output never enter the index), and run summaries — ranked by bm25 with titles weighted over bodies, a session collapsing to one hit however many of its messages match. Workflow definitions have no SQL representation (see *Workflow registry & run snapshots*), so they are matched from the in-memory registry at query time with the same substring semantics as the catalog filter. User input is tokenized into quoted prefix phrases before it reaches `MATCH`, so FTS5 operator syntax can't be injected and as-you-type prefixes match.
- **Workflow catalog (`/workflows`).** A searchable grid of every registered workflow, grouped by `group:`, each a launchable card showing its description and last-run status — the home for starting a workflow.
- **Session chat (`/sessions/:id`).** The conversation transcript with a composer, and a right rail carrying the session's editable title (committing a change renames it everywhere it's listed; clearing it restores the untitled fallback), its model — swappable mid-conversation, applying from the next turn, with a note on whether it accepts image input when known — its running token totals, current context fill, and the session's delete action.

Home has no right rail; per-route marginalia (an article's table of contents, a run's invocation inputs) appears only where a route has it. Cost visibility is deferred (see *Cost tracking* above).

## Application stack

The orchestrator is a single Node process serving both the engine and the UI. The user "uses the app" by visiting a local URL in their browser; the process keeps running regardless of whether that browser tab is open.

### Stack

- **Bun** — runtime. TypeScript runs natively (no separate compile step), `bun:sqlite` is statically linked (no native-module headache), and `bun build --compile` produces a single-file macOS binary — the release artifact for distribution. One toolchain for install, test, run, and build.
- **Hono** — HTTP server, SSE streams. Runtime-agnostic by design but pairs cleanly with Bun via `Bun.serve`. The Hono process *is* the orchestrator: executes workflow runs and session turns, serves the UI bundle. One process, clear ownership.
- **Vite + React** — UI bundle, served by Hono. No SSR, no framework magic — just a SPA window into the daemon. `wouter` for routing — tiny and hook-based.
- **SSE** for live feed updates. One-way (server → client), Hono has `streamSSE` built in. Browsers reconnect a *dropped* stream natively, but abandon one outright when a retry is answered with a non-200 or a wrong content type — and since the client's freshness comes from bus events alone, an abandoned stream would silently freeze every cached query until a reload. So the client watches for it: an abandoned stream is rebuilt with exponential backoff (capped at 30s), and focusing the tab retries at once rather than waiting the backoff out. Every open after the page's first counts as a reconnect and blanket-invalidates, recovering whatever was missed while disconnected — which is also why no `Last-Event-ID` replay is needed. WebSockets reserved for if/when bidirectional streaming is actually needed.
- **TanStack Query** for client state. The SSE bus carries thin events (a type plus ids); the client treats them as cache-invalidation signals — an event invalidates the affected query and React Query refetches — rather than hand-rolling per-surface refetch wiring. Freshness is driven by those events *alone*: queries carry an infinite stale time and refetch on neither focus, poll, nor remount. That keeps a cache from churning, at the cost of making the event stream load-bearing — a query no event invalidates is stale until a reload, not merely late. Shared data hooks live in `client/state/`; UI features under `client/features/` compose the design-system primitives, and each route renders its own page shell (left nav · main · right marginalia) rather than an app-level wrapper.
- **bun:sqlite + Drizzle** for state (see *State storage* under Architecture). Drizzle's `drizzle-orm/bun-sqlite` adapter; schema and migrations identical to a Node + better-sqlite3 setup.

No Next.js, no HonoX, no full-stack framework — explicit choice to keep UI and daemon as separate layers communicating over HTTP/SSE.

### Launch model & data dir

Kiri is a CLI launched from the cwd of whichever directory you want to run workflows against. The tool is global; the directory is the workspace. Same shape as `vite`, `next dev`, `drizzle-kit` — switching projects is `cd && kiri`, or set `KIRI_CONFIG_DIR` (a leading `~` is expanded) to pin a fixed workspace for launchers and aliases that can't easily `cd` first. There is no global cross-repo store. Workflow definitions are expected to live under git, but kiri itself doesn't enforce that — the user owns versioning their own definitions.

Repo-scoped runtime state lives in `.kiri/` at the repo root, gitignored:

```
<repo-root>/
  workflows/                  # YAML workflow definitions (in git)
  kiri.yaml                   # structured config: LLM providers, … (in git; optional)
  bundles/                    # script bundles (in git)
    claude-code/              # an example bundle copied in; user owns it
      run.sh
      README.md
    <other-bundles>/...
  prompts/                    # CC prompt templates (in git, convention only — any path works)
  .kiri/                      # gitignored — repo-scoped runtime state
    state.db                  # SQLite
    runs/<id>/                # per-run scratch dirs
    workflow.schema.json      # JSON Schema for workflows/*.yaml, rewritten every launch
    kiri.schema.json          # JSON Schema for kiri.yaml, rewritten every launch
    mcp-credentials.json      # OAuth tokens for MCP servers (mode 0600; separate from state.db)
    tool-permissions.json     # standing per-tool permissions (allow/off) for sessions (plain JSON; tool names aren't secrets)
```

Startup scaffolds `workflows/` and `.kiri/` at cwd if either is missing, then opens and migrates the state DB. No gates — a fresh `cd && kiri` just works, and the empty `workflows/` itself signals "nothing defined yet."

### Process model

Closing the browser tab does not kill the orchestrator. Killing the Hono process does. Matches the app-active constraint: orchestrator runs while the user is "at the keyboard" (i.e. has the daemon up), and stops cleanly when they're done. No background daemon, no launchd entry.

### Local URL & HTTPS

Canonical entry point is `https://local.kiri.build` — a tiny hand-maintained HTML shell hosted on Cloudflare Pages. The shell loads the locally-running kiri's app bundle from `http://127.0.0.1:4242/app.js` + `/app.css` (cross-origin, with `crossorigin="anonymous"`) and the bundle calls the API on the same local origin. Pages auto-provisions the cert on the custom domain; no embedded ACME, no DNS-01 challenge, no on-host TLS termination.

The split is what makes this trivial: Pages serves a single static shell file; kiri itself is unchanged HTTP on `127.0.0.1`. CORS allow-list on the kiri server permits `https://local.kiri.build` (plus `http://127.0.0.1:4242` and `http://localhost:4242` as fallbacks), and the shell's bundle paths are stable (`app.js`, `app.css`) so the shell needs no rebuild when kiri updates.

Browser caveat: Safari and Brave block HTTP-localhost subresource loads from an HTTPS page (mixed-content / private-network policies). On those browsers the fallback is the direct `http://localhost:4242` URL. A local-served HTTPS recipe (mkcert) is a possible future follow-on but not built.

### Future: native shell

Web-first for v1. Completion notifications already ride the browser's Notification API (opt-in, delivered only while a kiri tab is open). If/when notifications attributed to kiri rather than the browser, menu bar presence, or a real "app icon" become worth the effort, wrap the same Hono+React+Vite app in **Tauri 2** — minimal change to the codebase, native integration where it matters. Not a v1 commitment, just a path that stays open.

## Security

Script execution is the central capability of this system, which means security is not a bolt-on layer — it's a design constraint that shapes every surface. The threat model assumes:

- Workflow inputs (from polled external content, upstream step output, or anywhere user-controlled bytes can land) are untrusted data.
- Polled external content (PR titles, issue bodies, file contents from third-party repos) is untrusted.
- AI agents may attempt actions outside their intended scope due to prompt injection, misalignment, or simple error.
- The local machine is otherwise trusted (this is a personal tool on the user's own laptop).

### Trust boundaries

- **Workflow definitions, prompts, and scripts** (files in git) are *trusted*. They are reviewed and version-controlled.
- **Workflow inputs** at runtime are *untrusted*. They come from external polling or upstream step outputs that may have processed third-party data.
- **AI outputs** are *untrusted*. Even from a tightly-scoped agent, output is data, not commands. When it flows downstream as input to another step, it must be treated as untrusted input.

### Script execution

- **No shell interpolation of inputs.** Workflow inputs are passed via env vars or argv arrays, never spliced into shell command strings. The orchestrator constructs argument lists, the OS handles them, no shell parsing of user-controlled strings.
- **Per-step working directory.** Each workflow run gets a scratch directory; the step's cwd is set there, not the user's home or the orchestrator repo.
- **Per-step env scope.** Steps only see env vars from the step's `env:` block plus a small kiri-controlled set (`KIRI_RUN_ID`, `KIRI_STEP_INDEX`, `KIRI_REPO_ROOT`) and the OS essentials (`PATH`, `HOME`, `USER`, `LOGNAME`). No other parent-process env leaks through.
- **Env precedence at spawn.** User-declared `env:` is applied first; kiri- and OS-controlled vars overwrite on key collision. A workflow can't redirect `PATH` to inject a malicious binary or shadow `KIRI_RUN_ID` to confuse run identity.
- **Reserved namespace.** `env:` keys starting with `KIRI_` are rejected at workflow load time as a schema error. Typos and accidental collisions surface as load failures, not silent overwrites at spawn.
- **No resource limits.** ulimit/rlimit caps on step execution are deliberately not built (see *Out of scope*) — a runaway script is the user's own script on their own machine.
- **No kernel sandbox.** Bundles run with the user's permissions. The trust posture is "scripts you authored or pasted into your own repo, same as any shell script you'd run yourself" — sandbox-wrapping every step is cost without protection in that model. The defence here is reading the bundle before you use it, plus your own claude config for agent-spawning bundles.

### AI integration

- **Assume prompt injection.** PR bodies, issue text, file contents reaching an agent's prompt may attempt to redirect its behaviour. For a `claude-code` workflow step the load-bearing defence is the tool permissions in the user's own `~/.claude/settings.json` — even a fully compromised agent can only do what that config allows. Prompt-level mitigations (system prompt framing) help but aren't relied on as primary defence.
- **Conservative permissions.** Keep the global claude config an agent-spawning step runs under deliberate — broad `Bash(*)`-style allowances are a decision, never a quick fix to "make it work."
- **Session tools approved per call.** In agentic sessions, a tool injected via prompt-injection still can't run silently: unless its standing permission is `allow`, each call pauses for an explicit Allow / Always allow / Deny before it executes, and an `off` tool is never offered at all (see *Agentic sessions → Tool permissions*). Standing permissions live in a gitignored `.kiri/tool-permissions.json` — plain JSON, not a secret store — keyed by tool name and re-read on every call, managed from the Tools & MCP page or by editing the file.
- **Session file access is sandboxed and opt-in.** The filesystem tools exist only when `filesystem.allowed_directories` is declared in `kiri.yaml` — a git-reviewable boundary, like the `mcp:` block. Every model-supplied path — including one being created — resolves through symlinks and must land inside a declared directory, `.git` internals and secret-bearing files are unreachable outright (`.env*` and `.kiri/mcp-credentials.json` stay out of the transcript and the feed DB), and a failed config load empties the sandbox rather than widening it. Reads run on the sandbox's authority alone; every write, edit, or delete asks per call by default, with the exact change previewed as a diff at approval time (see *Agentic sessions → Session filesystem access*).
- **The session shell tool trusts the gate, not the model.** `run_command` executes model-authored commands, so its defences layer in that order: the core prompt holds the model to safe, goal-scoped commands — hard prohibitions, stated as such — and the per-call approval, previewing the exact command verbatim, is the boundary that holds even if the model is steered. The declared sandbox anchors where commands run, starting from the session's working directory; it is not claimed as containment. The opt-in `auto` permission sits above that boundary, never in place of it: a deterministic screen (comment-stripping, hard triggers no judgement can override) rules first, a context-starved utility-model judgement decides the remainder and fails closed to asking, and its worst case is exactly `ask` (see *Agentic sessions → Session shell commands*).

### Secrets

- **No secrets in workflow definitions.** Definitions are git-tracked. Secrets stay outside the repo, mode 600, referenced by name from the workflow.
- **No secrets in LLM provider config.** `kiri.yaml` is git-tracked, so an `api_key` is an `{ env: <NAME> }` reference only — a literal key is a schema error. Resolved values are never persisted, snapshotted, or echoed in errors (see *AI integration → LLM providers*).
- **MCP OAuth tokens are the one persisted-secret exception.** An `auth: oauth` MCP server's tokens are written to `.kiri/mcp-credentials.json` — gitignored, mode 0600, and a *separate* file from the state DB so secrets never land in queryable feed data. The trusted-local-machine threat model justifies on-disk tokens; the store sits behind a small interface so an OS keychain is a later swap. The OAuth callback (a top-level provider redirect, so a GET that can't carry the `X-Kiri-Client` header) is the one state-changing endpoint exempt from that CSRF gate — defended instead by the OAuth `state` parameter, which kiri validates against the value it persisted at sign-in start.
- **Don't print secrets to stdout.** Traces persist step output verbatim — there is no secret-pattern scrubbing. A step that echoes a token puts it in the feed DB.

### UI

- **All script and AI output is treated as untrusted.** No untrusted markup reaches the DOM without passing a sanitiser first. Markdown rendering uses a hardened parser with no raw-HTML pass-through — `dangerouslySetInnerHTML` is not used to inject parser output. The single place markup is embedded directly is a diagram's SVG, and only *after* a sanitiser has run over it (see *Mermaid diagrams*).
- **Charts carry no raw-HTML surface.** Fenced `chart` blocks in article markdown render Vega-Lite specs as SVG through that same parser — no `dangerouslySetInnerHTML`. Vega's data loader is locked to inline values, so a chart spec from untrusted article content cannot trigger a network fetch.
- **Mermaid diagrams are sanitised before embedding.** Fenced `mermaid` blocks render through mermaid in `strict` security mode, which runs the produced SVG through DOMPurify — stripping scripts and event handlers — before it is embedded inline. A malformed or hostile diagram degrades to an inline notice rather than breaking the article. The renderer offers a *source* view of the raw diagram text alongside the rendered diagram.
- **External links sandboxed.** `noopener noreferrer` on all outbound. No `javascript:` URLs.

### Operational hygiene

- **Orchestrator runs as the user.** No setuid, no elevated privileges. If a workflow needs more, it asks explicitly and the user approves once.
- **Definition repo treated as source code.** Reviewed PRs, signed commits where possible, no auto-merging of definition changes.

## Out of scope (v1)

Non-goals to resist scope creep:

- Branching, conditionals, fan-out/fan-in
- Auto-retry, DLQ
- Webhooks, inbox polling
- Multi-user, auth, sharing
- Global todo / inbox surface for cross-workflow proposed actions (recommendations attach to the producing run only)
- Dynamic per-call permission policy for **workflow steps** (an agent-spawning step runs under the user's global claude config — agentic sessions are the separate pillar that *does* gate tools per call, see *Agentic sessions → Tool permissions*)
- Persistent execution across app restarts (graceful halt on close, manual re-run on reopen)
- Custom DSL for workflows
- Agent-driven *workflow* control — workflows stay deterministic linear pipelines; no agent decides which step runs next. (Agentic behaviour is a separate pillar, see *Agentic sessions* — it does not reach into the workflow engine.)
- Pushing articles to external destinations (gist, git commit, webhook POST); `articles:` is in-app only for v1

Deliberately not built (single-user ephemeral local tool): audit logs, on-host HTTPS/TLS (the `https://local.kiri.build` shell is hosted, not on-host), `ulimit`/resource caps and kernel sandboxing of step execution, and a general secret store (secrets are env-var `{ env: }` refs). The one exception is MCP OAuth tokens, which *are* persisted — in a mode-0600 `.kiri/mcp-credentials.json` — because a browser sign-in has nowhere else to put them; a broader keychain-backed store stays out of scope until it's needed.

## Phased build

Sequenced for fastest path to dogfooding, then layering capability outward. Each phase a usable artifact.

**Shipped:**

1. **Spine.** YAML-defined linear pipeline of script steps. Standard envelope, traces captured, run history persisted to SQLite via Drizzle. Feed UI renders run history.
2. **Step schema migration.** YAML moved to `steps:` with `use:` (bundle reference) or `sh:` (inline shell), plus per-step `env:` with precedence and reserved-namespace rules.
3. **`claude-code` bundle starter.** A working CC runner bundle that translates `env:` keys to CC flags, spawns `claude`, and captures the session.
4. **Hosted shell.** `https://local.kiri.build` — a static Cloudflare Pages shell that loads the locally-running kiri's bundle. Stable bundle paths, CORS allow-list.
5. **Security baseline.** Bind to `127.0.0.1` only; require `X-Kiri-Client` header on state-changing endpoints — shuts down cross-origin attacks from other browser tabs.
6. **UX foundation + test infra.** Tailwind v4; `wouter` router with `/` and `/runs/:id`; `bun:test` + `happy-dom` + `@testing-library/react`; Playwright golden-path e2e.
7. **Live updates, toasts, cancel.** In-process event bus, SSE endpoint, EventSource cache invalidation, completion toasts, in-flight cancel.
8. **Activity feed summaries.** Workflow-level `summarize:` field, `claude-code-summarizer` bundle, summary rendered in feed and at the top of run detail.
9. **Onboarding & docs.** Hosted-shell fallback when no local kiri is running, one-sheet docs site at `/docs`, in-app link.
10. **Configurable summariser.** `PROMPT` / `PROMPT_FILE` / `MODEL` / `MAX_TURNS` env support on `claude-code-summarizer` with defaults preserved; `PROMPT` added to `claude-code` with precedence over `PROMPT_FILE`.
11. **Cursor-based feed pagination.** Infinite-scroll feed; live updates and cold-load cost decoupled from total run count.
12. **Article publishing.** `publish: [...]` array on workflows. Markdown articles stored in `articles`, surfaced as a stacked list on each feed row and a "Published" section on run pages, opened on dedicated `/runs/:id/published/:slug` pages via a sandboxed renderer.
13. **Workflow inputs.** `inputs:` block on workflows — named parameters collected via a modal on invoke, snapshotted onto the run, and injected into step `env:` via `{ input: <name> }` refs. One definition, many targets.
14. **Recommendations.** Workflows emit follow-up workflow invocations via a `KIRI_RECOMMENDATIONS_FILE` file channel. Stored as rows linked to the producing run, surfaced on the run detail page as a "Recommended" section beneath the run's phases, and triggered via the standard invoke modal with inputs pre-filled.
15. **First-party LLM steps.** An `llm:` step kind that runs a model completion in-process against a provider declared in `kiri.yaml` (`provider:model` ids, `{ env: <NAME> }` API-key refs). Inline or file prompts with the bundles' `{{VAR}}` templating — `{{KIRI_INPUT}}` for pipeline steps, ref-resolved env vars everywhere, the `{{KIRI_SUMMARY_CONTEXT}}` digest on summarise — token usage on the envelope, and a zero-config `llm:` summariser. The bundle-free path for completion-shaped steps; the model, prompt source, and token counts render across the run timeline and workflow schema surfaces.
16. **Agentic sessions.** The second pillar (see *Agentic sessions*) — multi-turn agentic chat against a model declared in `kiri.yaml`: streaming turns, cancel and resume, per-session token totals, one-click session creation, and a mid-conversation model swap. Sessions join workflow runs in the blended activity feed.
17. **Session system prompt.** A layered system prompt for sessions (see *Agentic sessions → System prompt*): an immutable kiri core layer (identity, environment, response and honesty guidance, markdown + chart + diagram rendering, untrusted-content framing), a workspace-root `kiri.md` of standing instructions, and optional `personas/<name>.md` overlays attached per session and swappable from the session aside — the persona overlays were later removed unused, in favour of on-demand instruction packs. Composed fresh each turn (core → `kiri.md`).
18. **Session tools — web search and extract.** The session tool loop (see *Agentic sessions → Tools*): tools plug into the AI SDK tool loop, with calls and results persisted as message parts and rendered inline in the transcript as a collapsed block, and the core prompt gains tool nudging plus chart/diagram restraint. The first tools were Tavily-backed **web search** and **web extract** — later removed in favour of MCP (see below).
19. **MCP server support.** Agentic sessions gain tools from **MCP servers** declared under `mcp:` in `kiri.yaml` — `stdio` subprocesses or `http`/Streamable-HTTP endpoints, secrets as `{ env: }` refs. Kiri connects each at boot and on config reload via `@ai-sdk/mcp`, namespaces their tools `<server>__<tool>`, and offers them to the session model; connection status surfaces as config-health checks.
20. **Retire first-party web tools.** The Tavily-backed web search/extract tools and the built-in tool seam are removed; the session tool catalogue is MCP-provided. Web search is now an MCP server the user plugs in (the Tavily MCP server) rather than a first-party tool.
21. **OAuth-authenticated MCP servers.** An `http` MCP server can set `auth: oauth` to authenticate by a browser OAuth sign-in instead of a static header. Kiri runs the flow — dynamic client registration, PKCE, refresh — through the official `@modelcontextprotocol/sdk`'s Streamable-HTTP transport (robust against real servers' discovery quirks where `@ai-sdk/mcp`'s OAuth is not), fed into `@ai-sdk/mcp`'s client so tools still arrive as an AI-SDK ToolSet. Tokens persist in a mode-0600 `.kiri/mcp-credentials.json`; a server awaiting sign-in — or one whose tokens later expire beyond refresh — surfaces as a one-click **Connect** prompt in the activity view and reconnects live on completion.
22. **Tool permissions.** Each tool in an agentic session carries a standing permission — `allow`, `ask` (default), or `off` — keyed by `<server>__<tool>` and persisted in a gitignored `.kiri/tool-permissions.json`. An `ask` tool gates per invocation: the turn pauses and the transcript shows an **Allow / Always allow / Deny** prompt before it runs (Allow once, Deny refuses and tells the model so, Always allow flips it to `allow`); an `allow` tool runs without prompting; an `off` tool is withheld from the model entirely. Managed from the **MCP page**, which lists each server and its tools with an Always allow / Ask / Off control, or by editing the file. Built on the AI SDK's native tool-approval flow — the request rides the existing turn stream and a verdict resubmits to resume — with permissions read on every call so a change takes effect next turn.
23. **Bounded, cancellable tool calls.** Every MCP tool call is wrapped so its result is capped at 128 KB (truncated with a marker past it) — a large payload can't overrun the model's context or the provider's request-size limit — and given a 180-second budget that rides the model's own cancel signal, after which the call is aborted and reported as a tool error the model can work around. A still-running turn can be cancelled by pressing Escape, which marks any call in flight cancelled rather than leaving it sitting on "working".
24. **Session context efficiency.** Send-time transforms over a turn's outbound history (stored messages untouched): tool-result culling past 80% of the known context window (delegate reports exempt), lossless TOON re-encoding of JSON results where smaller, `structuredContent` dedup so a result isn't paid for twice, and the context-footprint fill gauge in the session aside.
25. **Data-flow rework.** Named step `id`s with `{ step: <id> }` / `{ article: <slug> }` env refs — backward-only, load-validated, never truncated; runs made fail-fast end to end (a failed step skips articles and the summariser; a failed article entry fails the run and halts the rest); the `KIRI_SUMMARY_CONTEXT` digest injected into `summarize:`; the `KIRI_RUN_CONTEXT` file/inline channel retired.
26. **`articles:` rename.** The `publish:` workflow block renamed to `articles:` across schema, runner, UI, and docs — the block declares what a run produces, not where it goes.
27. **Articles decoupled from runs.** `articles` rows link to their producer via nullable `runId`/`sessionId` (XOR-checked) rather than a required run id, article links render in the run body, and the article page route moved to `/runs/:id/articles/:slug` — groundwork for session-produced articles.
28. **Session-written articles.** Five first-party session-scoped article tools (create/replace/edit/list/read, the edit an exact-string replacement) exercise the `sessionId` producer column, un-gated by tool permissions. Session articles get their own reading pages, a live articles panel in the session rail, and article links on session feed rows; `article.written` events keep every surface — mounted or not — in sync, and the turn-step cap rose to 32 for longer tool work.
29. **Session workflow tools.** First-party `list_workflows` and `run_workflow` tools — the sanctioned bridge between the pillars. Listing serves the registry's workflows with their declared inputs; running validates inputs through the invoke endpoint's schema, executes through the ordinary runner as a first-class run, blocks until it settles, and reports a compact outcome, with a turn abort cancelling the run. `run_workflow` executes user scripts, so it rides the standing tool-permission machinery (`ask` by default) and the MCP page gains a **Built-in tools** card to review and change it.
30. **Built-in tools under standing permissions.** Every first-party session tool joins the standing-permission surface: a builtin-tool registry declares each tool's blurb and default permission (`allow` for the kiri-data tools, `ask` for `run_workflow`), the session routes gate every tool — MCP and built-in — through one wrapper, and the permissions page's Built-in tools card (collapsed by default) lists them all. With built-ins alongside servers the page outgrew its name, so the nav item and page became **Tools & MCP**. The permission store gains caller-supplied fallbacks and persists an explicit `ask`, so overriding an `allow` default sticks.
31. **Session-authored workflows.** Sessions formalise conversation work into workflows through five first-party tools (see *Agentic sessions → Session-authored workflows*): a whole-YAML authoring interface (`create` / `edit` / `replace` behind the loader's own validation gate, shared via `parseWorkflowSource`; `read_workflow` off the registry's new source map), plus a `read_workflow_authoring_guide` tool that serves the deep authoring reference on demand — progressive disclosure instead of a system-prompt layer. Write tools default to `ask`; the guide makes model selection ask-first, and unknown-provider rejections name the configured set.
32. **Session run reruns.** A first-party `rerun_workflow` tool re-executes a settled run in place — same run id, same feed entry — through the runner's rerun path (the wipe helper shared with the rerun endpoint plus row reuse), validated against the workflow's current definition, `ask` by default. Guidance at each decision point (run_workflow's description, the system prompt's workflow layer, the authoring guide's working method) routes repeat and test executions through it, so authoring iteration evolves one feed entry instead of flooding the feed.
33. **Session filesystem read tools.** Four first-party tools — `find_files`, `list_directory`, `read_file`, `search_files` — give sessions read access to the user's files (see *Agentic sessions → Session filesystem access*), confined to a declarative `filesystem: allowed_directories` sandbox in `kiri.yaml` (workspace-relative, `~` expanded, opt-in: no declaration or no existing directory withholds the tools). Absolute-path currency both ways, realpath containment against `../` and symlink escapes, hidden paths unreachable, capped results, `allow` by default; a core-prompt guidance layer enumerates the reachable roots. Alongside: tool errors now stream their real text into the transcript instead of the SDK's masked default.
34. **Session filesystem write tools with rich diffs.** Five mutating first-party tools — `write_file`, `edit_file`, `create_directory`, `delete_file`, `delete_directory` — complete the filesystem set (see *Agentic sessions → Session filesystem access*): the same sandbox and containment guard, a not-yet-existing path confined through its nearest existing ancestor, deletes never touching an allowed root, all `ask` by default. Overwrites and edits return a unified diff that the transcript renders and the approval prompt previews — via a new design-system `Diff` primitive — while `toModelOutput` and a send-time history strip keep it out of everything the model receives.
35. **Session image generation.** Model listings classified by output modality — text or image, across the main vendor shapes, with unusable modalities (audio, video, embeddings) dropped — narrowing the session picker to text models and feeding a new per-session image-model picker beside it. `resolveImageModel` builds against providers' OpenAI-style images endpoint, and a `generate_image` tool (`allow`, offered only while an image model is selected) returns a data-URL result rendered full-width in the transcript, with `toModelOutput` and a send-time strip keeping the bytes out of the model's context.
36. **Search.** Cross-entity search over everything kiri accumulates (see *UI → Search*): a trigger-synced FTS5 index (`search_fts`) over article names and bodies, the text of user/assistant session messages, and run summaries — bm25-ranked, titles over bodies, snippets with highlighted matches — plus workflow definitions matched from the registry at query time. Served by `GET /api/search` with operator-proof query tokenization, and surfaced as a modal overlay (home search box, or ⌘K/Ctrl+K on any page) with debounced as-you-type results grouped by kind and walkable from the keyboard. Alongside: open dialogs now lock the page scroll behind them.
37. **Delegated child sessions.** A first-party `delegate` tool (see *Agentic sessions → Delegation*) whose server-side execute runs a self-contained task in a child session — sessions gain `parent_session_id` lineage — through the ordinary turn loop, resolving with only the worker's report so the parent's context holds findings, not working. Workers run the focused worker prompt and hold only standing-allow tools (delegation never widens what runs unprompted); a parent-turn cancel cascades in. Children are hidden from the feed, list, and search index yet live at their own URL, and the transcript renders each call as an embedded child-session box — live status, expandable transcript, per-task cancel — found via a children lookup keyed on the spawning call.
38. **Named outputs and `kiri-recommend`.** Declared `outputs:` on main `sh:`/`use:` steps, emitted through the `kiri-output` per-run PATH shim into a step-scoped channel file; `{ step: <id>, output: <name> }` env refs load-validated against the declaration; an ok exit missing a declared name fails the producing step; emitted maps persisted on `run_steps.outputs` and rendered in the run page's expanded step row; a sibling `kiri-recommend` shim replaces hand-assembled recommendation JSON with validated flags.
39. **Refs-only data flow.** The stdin pipeline removed (steps spawn with empty stdin; `{{KIRI_INPUT}}` retired) and `KIRI_SUMMARY_CONTEXT` with it — the whole-run digest was token-hungry by construction, and zero-config summarize existed only to prompt over it, so every llm entry now requires an explicit prompt. Env refs are the single data-passing channel across steps, articles, and summarize.
40. **Skills.** On-demand instruction packs for sessions (see *Agentic sessions → Skills*): `skills/<name>/SKILL.md` in the committed config dir, standard frontmatter (`name` defaulting to the directory, `description`, unknown fields ignored), listed in the system prompt as name + description only and loaded in full through a read-only `use_skill` built-in (`allow` by default, so workers inherit it through delegation's allow-only rule). First-party skills ship alongside — the workflow-authoring reference is the first, retiring the `read_workflow_authoring_guide` tool — and a user skill sharing a first-party name wins.
41. **Auto shell permission.** A fourth standing permission, offered on `run_command` alone (see *Agentic sessions → Session shell commands*): each call is decided per command by a deterministic screen — comment stripping, non-overridable hard-ask triggers, an exact always-allow list — with the remainder judged by the utility model, context-starved and failing closed to the ordinary approval prompt. No configured `models.utility` means `auto` behaves as `ask` outright; decisions are logged with reasons, and workers continue to inherit only `allow` tools.

## Open questions

- **Trace retention policy.** How long do verbose traces and CC transcripts stay in SQLite before pruning? Size-cap, time-cap, or both? Decision triggers the disk-blob split.
- **Secret store mechanism.** Resolved for the case that forced it: MCP OAuth tokens persist in a mode-0600 `.kiri/mcp-credentials.json` behind a small store interface (an OS keychain is a swap behind it). Other secrets stay env-var `{ env: }` refs. Still open is whether a broader keychain / 1Password integration is worth the friction for those — revisit if env-only secrets become painful.
